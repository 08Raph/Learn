#LESSON Android development | 13
**Android** runs on phones, tablets, watches, televisions and cars from hundreds of manufacturers. Apps are written mainly in **Kotlin**, built with **Gradle**, and developed in **Android Studio**, which is free.

### The building blocks
An Android app is a set of **components** declared in a file called the **manifest**.

- An **activity** is a screen with a user interface. Modern apps often have a single activity that hosts every screen.
- A **service** does work without a user interface, such as playing music.
- A **broadcast receiver** reacts to system events such as "charging started".
- A **content provider** shares structured data with other apps.

Components are started by **intents**: messages that say "open this screen" (explicit) or "something that can share a photo" (implicit, and the system offers the matching apps).

### The activity lifecycle
The system, not your code, decides when an activity lives and dies.

```diagram
   created --> started --> resumed (visible and interactive)
      ^           ^           |
      |           +-- paused -+     another window partly covers it
      +---- stopped <---------+     no longer visible
                |
            destroyed            also on screen rotation, by default
```

Rotating the screen destroys and recreates the activity. Anything held only in its fields is lost. State that must survive belongs in a **ViewModel** (survives rotation) and, for anything important, in saved state or storage (survives the process being killed).

### Jetpack Compose
Android's modern UI toolkit is **declarative**. You write functions that describe the screen for the current state; when the state changes, the affected functions run again.

```kotlin
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) {
        Text("Pressed $count times")
    }
}
```

There is no code that finds a label and changes its text. The UI is a function of state. The older system, XML layouts updated by hand, is still found in existing apps.

### Resources and device variety
Screens differ in size and pixel density. Sizes are given in **density-independent pixels** (dp): 1 dp is one physical pixel on a 160 dpi screen and scales in proportion, so a 48 dp button is about the same physical size everywhere.

```text
pixels = dp × (screen dpi / 160)
```

Text, images and layouts are kept as **resources**, with alternatives selected automatically by language, screen size and dark mode.

### Permissions
Access to the camera, location, contacts and similar is denied until the user grants it **at run time**. Ask at the moment the feature is used, explain why, and keep working if the answer is no. After repeated refusal the system stops showing the prompt, and the app can only direct the user to settings.

### Background work
To protect the battery, Android restricts what apps do in the background. Deferred work (uploading, syncing) is scheduled with **WorkManager**, which runs it when conditions such as "on Wi-Fi" are met, even after a restart.

### Building and shipping
Gradle compiles the code and resources into an **Android App Bundle**, which is **signed** with your key and uploaded to Google Play. Different **build variants** (debug, release, free, paid) come from one code base.

> Key idea: Android creates and destroys your components as it sees fit. Keep state out of the screen, describe the UI as a function of state, and ask for permissions only when needed.
#Q What happens to an activity, by default, when the device is rotated?

* It is destroyed and recreated, so state held only in its fields is lost
- The app is uninstalled
! A ViewModel or saved state preserves what matters.
#Q A button is 48 dp wide. How many pixels is that on a 320 dpi screen?
- 48
* 96
- 160
! 48 × 320 / 160 = 96.

#LESSON iOS development concepts | 13
**iOS** runs on iPhone, with close relatives on iPad, Apple Watch, Apple TV and Mac. Apps are written in **Swift** using **Xcode**, which runs only on a Mac. That is a real constraint: to build and publish a native iOS app you need access to a Mac and a paid developer membership. You can still learn the concepts, and the Swift language itself, without one.

### Swift in brief
Swift is a compiled, statically typed language designed for safety.

```swift
struct Task: Identifiable {
    let id: Int
    var title: String
    var done = false
}

var first: Task? = tasks.first        // an optional: may be nil
if let task = first {
    print(task.title)                 // safely unwrapped
}
```

- **Optionals** make "no value" part of the type. The compiler will not let you use a value that might be missing until you have checked.
- **Structs** are value types: assigning one copies it. **Classes** are reference types.
- Memory is managed by **automatic reference counting**. Two objects that refer to each other strongly are never freed (a retain cycle); one side is marked `weak`.

### SwiftUI
Like Compose, SwiftUI is declarative.

```swift
struct CounterView: View {
    @State private var count = 0
    var body: some View {
        Button("Pressed \(count) times") { count += 1 }
    }
}
```

`@State` marks data the view owns; changing it recomputes `body`. The older framework, **UIKit**, with view controllers updated by hand, underlies a great many existing apps.

### The app lifecycle
An iOS app moves between **not running**, **inactive**, **active**, **background** and **suspended**. A suspended app is in memory but executes no code, and the system may remove it without notice when memory is short. Save state when moving to the background; you will not be told when the end comes.

### The sandbox
Every app runs in a **sandbox**: its own directory and no access to other apps' files. Sharing happens through controlled system services such as the share sheet and document picker. Secrets are stored in the **Keychain**, encrypted by the system. Access to location, photos, the microphone and tracking needs permission, with a purpose string you write shown to the user.

### Layout
Layouts must adapt to many screen sizes, to the **safe area** (clear of the notch and home indicator), to **Dynamic Type** (the user's chosen text size) and to both orientations on iPad. Sizes are in **points**, which map to 1, 2 or 3 pixels according to the screen.

### Distribution
Apps are **code signed** with a certificate from Apple, tested with outside users through **TestFlight**, and submitted to the App Store, where each version goes through **review** against published guidelines. Rejections are common for crashes, unclear permission requests and incomplete information.

### What the two platforms share
| Concept | Android | iOS |
|---|---|---|
| Language | Kotlin | Swift |
| Declarative UI | Jetpack Compose | SwiftUI |
| Unit of size | dp | point |
| Secure storage | Keystore | Keychain |
| Background work | WorkManager | Background tasks |
| Store | Google Play | App Store |

The names differ and the ideas match. Learning one platform well makes the other much easier.

> Key idea: iOS apps are sandboxed, signed and reviewed, and can be suspended or removed at any time. Swift's optionals and value types remove whole classes of bug.
#Q What does a Swift optional express?
- That a variable is constant
* That a value may be absent, and must be checked before use
- That a function is asynchronous
! The compiler enforces the check.
#Q What do you need in order to build and publish a native iOS app?
- Any computer with a browser
* A Mac running Xcode and a developer membership
- An Android phone
! Xcode is available only on macOS.

#LESSON Designing interfaces for touch | 12
A phone is held in one hand, used in sunlight, on a train, in short bursts, with a thumb that covers what it touches. Interfaces designed for a mouse fail there.

### Touch targets
A fingertip is about a centimetre wide and imprecise. Both platforms give a minimum size for anything tappable:

- Android: **48 × 48 dp**.
- iOS: **44 × 44 points**.

The visible icon may be smaller, but the touchable area must not be. Leave space between targets so that a near miss does not hit the neighbour.

### Reach
On a large phone held in one hand, the thumb comfortably reaches the lower half of the screen. That is why primary navigation moved to the **bottom** (tab bars, bottom navigation) and why the main action often floats near the lower right.

### Navigation patterns
- **Tabs** at the bottom for three to five top-level sections.
- A **stack**: tapping an item pushes a detail screen; back pops it.
- **Modal** screens for a self-contained task that must be completed or cancelled.

Respect each platform's back behaviour. Android has a system back gesture; iOS relies on a back button and an edge swipe.

### Gestures
Taps are discoverable; swipes, long presses and pinches are not. Use gestures as **shortcuts** for something also available visibly, and follow platform conventions (pull to refresh, swipe to delete).

### Adaptive layout
One layout cannot serve a small phone and a tablet. Layouts change at **breakpoints**; Android's guidance uses width classes:

```text
compact    under 600 dp     one column, bottom navigation
medium     600 to 839 dp    navigation rail, perhaps two panes
expanded   840 dp and over  list and detail side by side
```

Within a screen, space is shared **flexibly**: each element has a base size, and leftover space is divided according to weights. This is the same model as CSS flexbox.

### Text entry is expensive
Typing on glass is slow and error-prone.

- Ask for less. Every field removed raises completion.
- Show the right keyboard (number, email).
- Support autofill and password managers.
- Offer pickers, toggles and sensible defaults.
- Validate as the user goes, with messages beside the field.

### Feedback and state
Every touch should produce a visible response within about a tenth of a second. Each screen has more states than the happy one: **loading**, **empty**, **error**, **offline** and **partial**. Design all of them. A blank screen is the commonest design bug in mobile apps.

### Accessibility
- Label every control for screen readers (TalkBack, VoiceOver).
- Respect the user's text size; layouts must not break at 200%.
- Keep text contrast at 4.5:1 or better.
- Do not convey meaning by colour alone.
- Honour "reduce motion".

### Follow the platform
Users bring habits from every other app on their phone. Material Design (Android) and the Human Interface Guidelines (iOS) describe what they expect. An app that follows them feels familiar at once.

> Key idea: Design for thumbs, small screens and interruptions: large targets within reach, little typing, every state designed, and platform conventions followed.
#Q What is the minimum recommended touch target on Android?
- 24 × 24 dp
* 48 × 48 dp
- 100 × 100 dp
! Smaller targets are hard to hit reliably.
#Q Why is primary navigation usually placed at the bottom of a phone screen?
- It looks more modern
* It is within easy reach of the thumb when the phone is held in one hand
- The top is reserved by the system
! The lower half of the screen is the comfortable zone.

#LESSON App architecture | 12
A mobile app is long-lived, stateful, asynchronous and regularly destroyed by the system. Without structure, logic ends up tangled in screen code that cannot be tested.

### Separate the layers
```diagram
   UI layer         screens that display state and send user events
        |  ^
   events  state
        v  |
   presentation     view models: hold screen state, handle events
        |
   domain           business rules (optional in small apps)
        |
   data layer       repositories over the network and local storage
```

Each layer depends only on the one below it. The UI knows nothing about HTTP; the data layer knows nothing about screens.

### MVVM and unidirectional data flow
In **Model-View-ViewModel**, a **view model** holds the state of one screen and exposes it as an observable value. The view displays that state and forwards user actions. It contains no logic of its own.

Data moves in **one direction**:

```diagram
   state --> view --> user event (intent) --> view model --> new state
```

The screen is always a function of a single state object:

```kotlin
data class TasksUiState(
    val items: List<Task> = emptyList(),
    val loading: Boolean = false,
    val error: String? = null
)
```

Because the state is one immutable value, impossible combinations are easy to rule out, every change is traceable, and the view model can be **unit tested** with no device: send an event, assert on the state.

### Repositories
A **repository** hides where data comes from. A common rule is the **single source of truth**: the screen observes the local database only. The repository fetches from the network and writes the result into the database, and the screen updates because the database changed. The app works offline with no special cases.

### Asynchronous work
The **main thread** draws the interface. Blocking it for more than a few milliseconds freezes the app, and the system may offer to close it. Network and disk work runs elsewhere, using **coroutines** in Kotlin and **async/await** in Swift, tied to a scope so that work is cancelled when its screen goes away. Forgetting to cancel leaks memory and updates screens that no longer exist.

### Dependency injection
A view model should **receive** its repository, not construct it. Then a test can pass a fake one. Frameworks automate the wiring, but the principle is only "pass dependencies in".

### Navigation
Treat navigation as state too: a **back stack** of destinations. **Deep links** map a URL to a destination, and the stack beneath it must be rebuilt so that back behaves sensibly.

### Native or cross-platform
- **Native** (Kotlin and Swift): best platform fit and access to everything, two code bases.
- **Kotlin Multiplatform:** share business logic, keep native UI.
- **Flutter** and **React Native:** share the UI too, with their own trade-offs in fidelity and dependence on the framework.
- **Web apps (PWAs):** one code base and no store, with limited access to device features.

Choose by team skills, required platform features and budget. There is no universal answer.

> Key idea: Keep logic out of the screen. A view model turns events into a single immutable state, repositories hide data sources, and dependencies are passed in so that everything can be tested.
#Q In unidirectional data flow, how does the view change what is displayed?
- It modifies its own widgets directly
* It sends an event to the view model, which produces a new state that the view displays
- It writes to the database
! State flows down and events flow up.
#Q Why should long-running work stay off the main thread?
- The main thread is slower
* The main thread draws the interface; blocking it freezes the app
- Background threads use less battery
! A frozen interface may be reported as "not responding".

#LESSON Navigation, lifecycle and state | 13
### Apps do not own their own lives
A desktop program runs until you close it. A mobile app is started, paused, hidden and killed by the operating system, often without warning, to save memory and battery. Designing for that is a core mobile skill.

### Lifecycle
Both platforms move each screen through states:

- **Android:** an Activity is created, started (visible), resumed (in front, receiving input), then paused, stopped and possibly destroyed. Rotating the device destroys and recreates the Activity by default.
- **iOS:** the app is active, inactive (an incoming call), in the background (a few seconds to finish work) or suspended (frozen in memory), and a suspended app can be terminated at any time.

Respond to these events: pause video and animations when hidden, stop location updates you no longer need, and save unsaved work when moving to the background.

### Process death
The surprising case: the user switches to the camera, the system kills your app to free memory, and later the user comes back. The OS shows your app as if it never left, so it must **restore** where the user was: the screen, scroll position and text typed into a form.

- Android: `onSaveInstanceState` and `SavedStateHandle` in a ViewModel store small pieces of state that survive process death.
- iOS: state restoration APIs and SwiftUI's `@SceneStorage` do the same.

Keep only small identifiers there (which item was open), not large data; reload the data from the local database.

### Navigation
Apps are stacks of screens. Pushing a screen adds it to the **back stack**; going back pops it. Tabs give each section its own stack. Good navigation means:

- Back always does what users expect, including the Android system back gesture.
- Deep links, such as a notification that opens a specific order, build a sensible back stack behind the target screen, so back leads somewhere reasonable rather than out of the app.
- Navigation is described in one place (a navigation graph or router), not scattered through screens.

### Where state should live
UI state that a screen needs should live in a **ViewModel** (or an observable model in SwiftUI) that outlives rotations, not in the view itself. Data that must outlive the app lives in storage. Mixing these up causes the classic bugs: forms that empty when the phone rotates, and screens that show stale data after returning.

### Worked example
Restoring a half-written message after the system kills the app.

```text
User types a long message → switches to the camera → system kills the app.
Before: onSaveInstanceState / SceneStorage stored:
          screen = "compose", draftId = 88
Draft text itself was saved to the local database every 2 seconds.
User returns: app restarts, reads screen + draftId, loads draft 88 from the
database, and shows the compose screen exactly as it was.
```

Store tiny identifiers for restoration and keep real data in storage; then process death becomes invisible to the user.

> Key idea: The OS controls the app's lifecycle and may kill it at any time. Save small UI state for restoration, keep data in storage, design a predictable back stack, and keep screen state in a model that survives recreation.
#Q On Android, what happens to an Activity by default when the device is rotated?

* It is destroyed and recreated
- The app is uninstalled
! Configuration changes recreate the Activity unless state is kept elsewhere.
#Q What is process death?
- A crash caused by a bug
* The system killing a background app to free memory, after which the app must restore its state when reopened
- Uninstalling the app
! The user expects to return to where they were.
#Q A notification opens order 42 deep inside the app. What should the back button do there?
- Close the app immediately
* Go back through a sensible stack, such as the orders list
- Nothing
! Deep links should build a reasonable back stack.

#LESSON Cross-platform approaches | 12
### Two platforms, one team
Writing separate Kotlin and Swift apps gives the best platform fit but roughly doubles the work. Several approaches share code instead. None is free; each trades something.

### The main options
- **Native (Kotlin and Swift):** full access to every platform feature on day one, the best performance and platform feel. Two codebases, two skill sets.
- **React Native:** JavaScript or TypeScript with React. Components map to real native views, so apps look native. Large ecosystem; performance-sensitive parts may need native modules.
- **Flutter:** Dart, with its own rendering engine that draws every pixel. Consistent look across platforms and smooth animation; the app does not use native widgets, so matching platform conventions takes care, and app size is larger.
- **Kotlin Multiplatform:** shares business logic (networking, storage, rules) written in Kotlin, while each platform keeps a native UI. Less sharing, but no compromise on the interface.
- **Progressive web apps (PWAs):** a website that can be installed, work offline with a service worker and, on newer systems, send notifications. One codebase and no app store, but limited access to device features, especially on iOS.

### How to choose
Ask:

1. Which device features do you need: Bluetooth, background location, widgets, payments? Check each approach's support.
2. How important is platform feel and performance (games, heavy animation, camera)?
3. What does the team already know?
4. How long will the app live, and who maintains the bridges and plugins it depends on?

A content or form-based business app is often well served by React Native, Flutter or a PWA. An app central to a platform experience, or one depending on new OS features, often justifies native. Many companies mix: native shells with shared logic, or native screens inside a cross-platform app.

### What does not change
Whatever the approach, you still need the platform knowledge from earlier lessons: lifecycles, permissions, store review, accessibility, offline behaviour and release processes. A cross-platform framework hides the differences only until something goes wrong.

### Worked example
Choosing an approach for a new app with a weighted decision matrix.

```text
Criteria (weight)        Native  React Native  Flutter  PWA
Needs Bluetooth LE (3)      5         3          3      1
Team knows TypeScript (2)   2         5          2      5
UI consistency (1)          3         4          5      4
Time to first release (2)   2         4          4      5
Weighted total             27        33         27     27
Decision: React Native, with a native Bluetooth module.
```

Writing down the criteria and weights makes the trade-off explicit and easy to revisit if the requirements change.

> Key idea: Native gives the best fit at twice the work; React Native and Flutter share UI code with different trade-offs; Kotlin Multiplatform shares logic but not UI; PWAs avoid app stores but have limited device access. Choose by features, feel, team and lifetime.

#LAB js | Mobile UI and architecture logic
Implement the platform-independent logic behind a mobile screen.

- `dpToPx(dp, dpi)` returns pixels, rounded to a whole number: `dp × dpi / 160`.
- `touchTargetOk(widthDp, heightDp)` returns true if both are at least 48.
- `widthClass(widthDp)` returns `"compact"` (under 600), `"medium"` (600 to 839) or `"expanded"`.
- `flexRow(container, items)` lays out a row. `items` is `[{ basis, grow }]`. Each item gets its `basis`, and the space left over (container minus all bases) is shared in proportion to `grow`. If no item grows, each keeps its basis. Return the array of widths.
- `lifecycleNext(state, event)` models an Android activity: `"start"` moves `"created"` → `"started"`; `"resume"` moves `"started"` → `"resumed"`; `"pause"` moves `"resumed"` → `"started"`; `"stop"` moves `"started"` → `"created"`. Anything else leaves the state unchanged.
- `reduce(state, intent)` is a view model. State is `{ items, loading, error }`. Intents: `{ type: "load" }` sets `loading` true and `error` null; `{ type: "loaded", items }` sets the items and `loading` false; `{ type: "failed", message }` sets `error` and `loading` false and keeps the items. Unknown intents return the state unchanged. **Never mutate the state passed in.**
- `permissionNext(status, action)` models a run-time permission. Status is `"notAsked"`, `"granted"`, `"denied"` or `"deniedForever"`. Action `"allow"` gives `"granted"` unless the status is `"deniedForever"`. Action `"deny"` turns `"notAsked"` into `"denied"` and `"denied"` into `"deniedForever"`. `"granted"` and `"deniedForever"` never change.

  return true;
}

  return "compact";
}

}

  return state;

  return state;

@solution
function dpToPx(dp, dpi) {
  return Math.round(dp * dpi / 160);
}

function touchTargetOk(widthDp, heightDp) {
  return widthDp >= 48 && heightDp >= 48;
}

function widthClass(widthDp) {
  if (widthDp < 600) return "compact";
  if (widthDp < 840) return "medium";
  return "expanded";
}

function flexRow(container, items) {
  let used = 0, grow = 0;
  for (const i of items) { used += i.basis; grow += i.grow; }
  const free = container - used;
  return items.map((i) => (grow > 0 ? i.basis + free * i.grow / grow : i.basis));
}

function lifecycleNext(state, event) {
  if (state === "created" && event === "start") return "started";
  if (state === "started" && event === "resume") return "resumed";
  if (state === "resumed" && event === "pause") return "started";
  if (state === "started" && event === "stop") return "created";
  return state;
}

function reduce(state, intent) {
  if (intent.type === "load") return { items: state.items, loading: true, error: null };
  if (intent.type === "loaded") return { items: intent.items, loading: false, error: null };
  if (intent.type === "failed") return { items: state.items, loading: false, error: intent.message };
  return state;
}

function permissionNext(status, action) {
  if (status === "granted" || status === "deniedForever") return status;
  if (action === "allow") return "granted";
  if (action === "deny") return status === "notAsked" ? "denied" : "deniedForever";
  return status;
}

#LESSON Storing data on the device | 12
A mobile app that needs the network for everything is slow, and useless in a tunnel. Local storage makes an app fast and dependable. There are several kinds, for different jobs.

### Key-value storage
For small settings such as the chosen theme: **DataStore** or SharedPreferences on Android, **UserDefaults** on iOS. Simple, unstructured, and **not for secrets**: on a compromised device it can be read.

### Files
Each app has private directories. Use them for documents, downloaded images and exports. Distinguish data that must be kept from a **cache**, which the system may delete when space is short and which should not be included in backups.

### A relational database
For structured data that is queried, sorted and related, both platforms include **SQLite**, a complete SQL database in a single file. It is usually used through a library: **Room** on Android, **Core Data** or **SwiftData** on iOS, which map rows to objects and check queries.

A database gives transactions, indexes and queries, and can notify the interface when a query's results change, which is what makes the single-source-of-truth pattern work.

### Migrations
Version 2 of your app adds a column. Users' devices hold version 1 databases full of data they care about. A **migration** is a script that upgrades the schema from one version to the next, preserving the data.

```sql
-- migration from version 1 to 2
ALTER TABLE notes ADD COLUMN pinned INTEGER NOT NULL DEFAULT 0;
```

Rules:

- Number schema versions and write a migration for every step.
- Users skip releases. Someone on version 1 installing version 4 must run 2, 3 and 4 **in order**.
- Never edit a migration that has shipped.
- Test migrations against real old databases. A failed migration can destroy a user's data, and "delete everything and start again" is acceptable only for a cache.

### Secure storage
Passwords, tokens and keys go in the platform's protected store: the **Keystore** on Android, the **Keychain** on iOS. They are encrypted with keys held by hardware and can require the device to be unlocked or a fingerprint to be given.

### What to keep, and for how long
- Store what the app needs to work offline, not everything the server has.
- Give cached data a **lifetime**, and show its age when it matters.
- Cap the size of caches and evict the least recently used entries.
- Remove a user's data when they sign out.
- Remember that devices are backed up to the cloud: decide what should and should not be included.

### Synchronisation
If data can change both on the device and on the server, the two must be reconciled. Record local changes in an **outbox** and send them when online. Decide what happens in a conflict: last write wins, a merge, or asking the user. Give every change an identifier so that a retry cannot apply it twice.

> Key idea: Use key-value storage for settings, a database for structured data, and the secure store for secrets. Migrate schemas step by step and never lose the user's data.

- Only the version 4 migration runs
* Migrations 2, 3 and 4 run in order
- The database is deleted
! Each migration assumes the previous version's schema.
#Q Where should an authentication token be stored?
- SharedPreferences or UserDefaults
* The Keystore or Keychain
- A text file in the cache directory
! The secure store is hardware-backed and encrypted.

#LESSON Networking and APIs | 13
Mobile networks are slow, expensive, intermittent and change from moment to moment. Networking code must assume failure.

### Talking to an API
Most apps use **HTTPS** with JSON. Libraries handle the mechanics: **Retrofit** and **Ktor** on Android, **URLSession** on iOS. JSON is decoded into typed objects, and a response that does not match the expected shape is an error to handle, not a crash.

Never perform a request on the main thread, and give every request a **timeout**. A request without one can hang for minutes.

### Failures are normal
Classify them:

- **No connection**, a **timeout** or a **5xx** response: temporary. Retrying may work.
- **4xx** responses: the request is wrong. Retrying the same thing will not help. `401` means sign in again; `429` means slow down.

### Retrying safely
Retry temporary failures with **exponential backoff**: wait 1 s, 2 s, 4 s, 8 s, up to a maximum, and add random **jitter** so that thousands of phones do not retry at the same instant after an outage.

```text
delay = min(maximum, base × 2^attempt) + random jitter
```

Only retry operations that are **idempotent**. A retried "create order" must not create two orders: send an **idempotency key** that the server uses to recognise the repeat.

### Caching
The fastest request is the one not made.

- Honour HTTP caching headers (`Cache-Control`, `ETag`). A conditional request that returns `304 Not Modified` costs almost nothing.
- Show cached data at once and refresh it in the background (**stale-while-revalidate**).
- Give cached data a maximum age.

### Pagination
A list of ten thousand items is not downloaded at once. The API returns a **page** and a **cursor** for the next one, and the app loads more as the user scrolls. Cursors are more reliable than page numbers when items are being added.

### Being a good citizen
The radio is among the largest drains on the battery, and it stays powered for seconds after each use.

- **Batch** requests instead of trickling them.
- Defer non-urgent uploads until the device is on Wi-Fi and charging.
- Compress, and request only the fields and image sizes needed.
- Respect the user's data-saver setting.

### Real-time updates
For chat or live scores, use **push notifications** to wake the app, or a **WebSocket** while it is open. Do not poll every few seconds. Push delivery is not guaranteed and is delayed in low-power modes, so treat a push as a hint to synchronise, not as the data.

### Authentication
The usual pattern is a short-lived **access token** sent with each request and a long-lived **refresh token** kept in secure storage. When a request returns 401, refresh once and retry; if refreshing fails, sign the user out. Use the system browser for sign-in with OAuth, not an embedded web view, so that the app never sees the password.

### Test without the network
Put the API behind an interface and test against fakes that return errors, slow responses and malformed data. Use the platform's network conditioning tools to try the app on a bad connection, because that is where users are.

> Key idea: Expect requests to fail. Use timeouts, retry temporary failures with backoff and idempotency, cache aggressively, and spare the battery.
#Q Which failure should not simply be retried?
- A timeout
- A 503 response
* A 400 response
! The request itself is wrong; repeating it gives the same result.
#Q Why is jitter added to retry delays?
- To make debugging harder
* So that many clients do not all retry at the same moment
- To use more battery
! Synchronised retries can overwhelm a recovering server.

#LESSON Mobile security | 13
A phone holds messages, photos, location history and banking apps, and is easily lost. A mobile app also runs on a device the **attacker may control**: they can inspect its files, intercept its traffic and take it apart.

### The first rule: the client is not trusted
Anything shipped inside an app can be extracted. Therefore:

- **Never embed secrets.** An API key with real privileges, placed in the app, is public. Keys that must exist in a client should be restricted (by platform, by quota) and able to do only harmless things.
- **Enforce every rule on the server.** Checks in the app are for convenience only. Prices, permissions and limits are validated by the server on every request.

### Protect data at rest
- Tokens and keys in the Keystore or Keychain.
- Do not write personal data to logs. Logs are readable in more ways than you expect.
- Mark sensitive screens so that they do not appear in the app switcher's snapshot or in screenshots.
- Exclude sensitive files from cloud backups.
- Clear data on sign-out.

### Protect data in transit
- **HTTPS everywhere.** Both platforms block plain HTTP by default; do not switch that off.
- Never disable certificate validation "to make it work in testing". Such code reaches production.
- **Certificate pinning** makes the app accept only your server's key, defeating an attacker who has installed a rogue certificate authority. It raises the bar and adds operational risk: a mistake in rotating the key locks every user out.

### Platform entry points
Other apps and web pages can send your app input.

- **Deep links:** treat the URL as untrusted input. Validate the host and every parameter. A link must never perform a sensitive action (pay, delete) without confirmation.
- **Intents and exported components** (Android): export only what must be public.
- **Web views:** load only content you control, and expose no native functions to untrusted pages.
- **Clipboard:** other apps can read it. Do not put secrets there.

### Authentication on the device
**Biometrics** (fingerprint, face) are a convenient way to unlock a key held in secure hardware. The app does not see the fingerprint; it asks the system whether the user was verified. Always offer a fallback, and require re-authentication for high-risk actions.

### Permissions and privacy
Ask for the minimum, at the moment of need, with an honest explanation. Prefer approximate location to precise, a photo picker to full library access. Both stores require you to declare what data you collect, and misdeclaring it gets apps removed. Privacy law applies to mobile apps like any other software.

### Reverse engineering and tampering
Apps can be decompiled and modified. **Obfuscation** slows an attacker a little. **Integrity attestation** services let your server check that a request comes from a genuine, unmodified app on a genuine device. Use them for high-value operations, as one signal among several, never as the only defence.

### Dependencies
A typical app is mostly third-party libraries, each able to do anything the app can. Keep them few, updated and from reputable sources, and review what advertising and analytics libraries collect.

### A checklist
The **OWASP Mobile Application Security** project publishes a verification standard and a testing guide. Use them as a checklist before release.

### Worked example
Storing a login token securely on a phone.

```text
Wrong:  SharedPreferences / UserDefaults in plain text → readable from backups
        or on a rooted device.
Right:  Android Keystore / iOS Keychain hold the key; the token is encrypted with it.
Also:   short-lived access token (15 min) + refresh token
        certificate pinning only if you can update pins safely
        never ship API secrets in the app: anyone can extract them
```

Platform key stores protect secrets with hardware, while short-lived tokens limit the damage if one leaks; anything inside the app binary is public.

> Key idea: Assume the attacker holds the device and can read the app. Keep secrets out of it, enforce rules on the server, store tokens securely, and treat every incoming link as untrusted.

* Anything inside the app can be extracted by anyone who downloads it
- Keys expire quickly
! Apps can be unpacked and decompiled.
#Q How should an app treat the parameters of a deep link?
- As trusted, because the system delivered them
* As untrusted input that must be validated
- As encrypted
! Any web page or app can craft a link.

#LESSON Testing, release and operations | 12
A web application can be fixed in minutes. A mobile release passes through review and then depends on users installing the update: a serious bug can stay in people's hands for weeks. Testing and careful release matter more here than almost anywhere.

### The test pyramid on mobile
- **Unit tests** for view models, reducers and repositories. They run on your computer in seconds and should be the majority.
- **Integration tests** for the database and migrations, and for the network layer against a fake server.
- **UI tests** drive the real app on an emulator or device (Espresso and Compose testing on Android, XCUITest on iOS). They are slow and less reliable, so keep them to the critical journeys: sign in, the main task, purchase.

### The device matrix
Android alone has thousands of device models. You cannot test them all. Choose a matrix deliberately: the oldest supported OS version and the newest, a small and a large screen, a low-memory device. **Device farms** in the cloud run your tests on real hardware.

Test the conditions that emulators hide: a slow network, no network, low storage, an incoming call, rotation, the app being killed in the background, large text and dark mode.

### Versioning
Each release has a human-readable **version name** (`2.4.1`) and a **build number** that must increase with every upload. Compare versions numerically, part by part: `1.10.0` is newer than `1.9.0`, though a text comparison says the opposite.

The server must go on supporting old app versions, because users do not update at once. Version your API, and build in a way to tell very old clients that they must update.

### Signing
Every release is **cryptographically signed**. The signature proves that an update comes from the same developer as the installed app. Lose the signing key and you cannot update your app, so store it securely and use the stores' key-management services.

### Review and store rules
Both stores review submissions. Common reasons for rejection: crashes, broken links, permission requests without clear purpose, missing privacy information, and no way to delete an account. Allow time for review in your plans.

### Staged rollout
Do not release to everyone at once. Release to a small percentage, watch the health metrics, and widen in steps: 1%, 5%, 20%, 50%, 100%. Halt if the crash rate rises. Each user is assigned consistently, so the same people stay in the rollout as it grows.

**Feature flags** controlled from the server go further: ship the code switched off, turn it on gradually, and turn it off at once if it misbehaves, with no new release.

### Watching production
- **Crash reporting** collects stack traces with the device model and OS version, grouped by cause. Watch the **crash-free rate**.
- **Performance monitoring:** start-up time, frozen frames, network latency.
- **Analytics**, used with care and consent, to see where users give up.
- Store reviews and support requests.

Do not log personal data in any of them.

### Continuous integration and delivery
On every change, automation builds the app, runs the tests and static analysis, and produces a signed build for testers. Releasing becomes routine, which makes releases small, which makes them safe.

### Worked example
A release pipeline for a mobile app.

```text
On every pull request:   unit tests · lint · UI tests on 2 emulators
On merge to main:        build signed beta → TestFlight / internal testing track
Before release:          manual check on 3 real devices; accessibility pass
Release:                 staged rollout 1% → 10% → 50% → 100% over a week
Watch:                   crash-free users ≥ 99.5%; stop the rollout if it drops
Remember:                users keep old versions for months; the API must support them
```

Staged rollouts limit the damage of a bad build, and because you cannot force updates, server APIs must stay backward compatible.

> Key idea: A mobile release is hard to take back. Test the logic heavily and the critical journeys on real devices, roll out in stages, and watch crash rates.

#LESSON Push notifications and background work | 12
### How a push reaches the phone
An app cannot keep its own connection open to your server all day: that would drain the battery. Instead, each platform runs one shared, efficient connection to its own service:

- **APNs** (Apple Push Notification service) for iOS.
- **FCM** (Firebase Cloud Messaging) for Android.

The flow:

1. The app asks the OS to register for notifications and receives a **device token**.
2. The app sends that token to your server, linked to the signed-in user.
3. When something happens, your server sends a message with the token to APNs or FCM.
4. The platform service delivers it to the device, where the OS shows it or wakes the app.

Tokens change (reinstalls, restores, new devices), so the app should send the current token at every launch, and the server should delete tokens that the service reports as invalid.

### Permission and respect
On iOS, and on Android 13 and later, the app must ask permission before showing notifications, and many users say no. Ask **in context**, after explaining the benefit ("Get a message when your order ships"), not on first launch. Let users choose categories (Android **notification channels** make this a system feature), and never send marketing disguised as alerts: it is the fastest way to be switched off or uninstalled.

### Kinds of message
- **Visible notifications** carry a title and body that the OS displays even if the app is not running.
- **Data or silent pushes** carry only data and ask the app to wake briefly in the background, for example to sync new messages. Platforms throttle them and may not deliver them at all when the battery is low; never rely on them for anything critical.

Keep sensitive content out of notification text, which appears on the lock screen. "You have a new message" is safer than the message itself.

### Background work
Beyond pushes, apps often need to do work later: upload photos, sync, clean caches. Both platforms restrict background execution to protect battery:

- **Android:** WorkManager schedules deferrable work with conditions such as "on Wi-Fi and charging", and survives restarts.
- **iOS:** BackgroundTasks lets the system choose a good moment for refresh or processing tasks; time is limited and not guaranteed.

Design for the work to be **interrupted and resumed**, keep it idempotent, and never assume exactly when it will run.

### Worked example
The journey of one push notification.

```text
1. App starts → registers → receives device token "f3a9..." from FCM/APNs.
2. App sends the token to your server with the user ID.
3. A new message for that user arrives on the server.
4. Server → FCM/APNs: { token: "f3a9...", title: "New message", data: { chat: 77 } }
5. Platform delivers it; the OS shows the notification.
6. User taps it → app opens chat 77 (a deep link).
7. If FCM/APNs reports the token invalid, the server deletes it.
```

Your server never talks to the phone directly; it talks to the platform service using a token that can change and must be refreshed.

> Key idea: Pushes go from your server through APNs or FCM to a device token. Ask for permission in context, keep lock-screen text discreet, treat silent pushes as hints, and schedule background work with the system so it can be delayed or interrupted safely.

- The phone's IP address
* The device token the app registered and sent to the server
- The user's password
! APNs and FCM deliver by device token.
#Q When is the best time to ask for notification permission?
- Immediately on first launch
* In context, after explaining what the user will get
- Never; it is granted automatically everywhere
! Users agree more often when they understand the benefit.
#Q Why should a silent (data-only) push never carry critical work?
- It is always encrypted
* Platforms throttle and may drop them, especially on low battery
- It cannot contain data
! Delivery of background pushes is best effort.

#LESSON Performance and accessibility on mobile | 12
### The frame budget
At 60 frames a second, each frame has about **16 milliseconds** for everything: handling input, running your code, laying out and drawing. On 120 Hz screens it is about 8 ms. Miss the budget and scrolling stutters, which users call **jank**.

Keep the main (UI) thread free:

- Do network requests, database queries, image decoding and heavy calculation on background threads or coroutines.
- Recycle list rows (RecyclerView, LazyColumn, UITableView, List) instead of creating thousands of views.
- Load images at the size they are displayed, and cache them.
- Measure with the profilers in Android Studio and Xcode rather than guessing.

### Start-up time
Users judge an app in its first seconds. Do the minimum before showing the first screen: defer analytics, prefetching and non-essential setup until after it appears, and show cached content immediately.

### Battery and data
- Background work is restricted on both platforms; use the system schedulers (WorkManager on Android, BackgroundTasks on iOS) so the OS can batch work efficiently.
- GPS, the radio and the screen are the big consumers: ask for location only as precisely and as often as needed.
- Respect metered connections: large downloads on Wi-Fi, smaller images on mobile data.

### Accessibility
Mobile platforms have strong built-in assistive technology, and apps must cooperate with it:

- **Screen readers** (TalkBack on Android, VoiceOver on iOS) read each element aloud. Give icons and image buttons a text **label**, such as "Delete message" rather than "button".
- **Dynamic type:** users enlarge text in system settings. Layouts must grow with it, not truncate or overlap.
- **Touch targets** of at least about 44 to 48 points square, with space between them.
- **Contrast** of at least 4.5:1 for normal text, and never colour alone to convey meaning.
- Support **reduced motion** and do not rely on gestures that have no button alternative.

Test by actually turning on the screen reader and the largest text size and using the app. It takes minutes and finds most problems.

### Worked example
Fixing a janky scrolling list.

```text
Profiler: frames take 35 ms while scrolling (budget 16 ms).
Cause 1:  each row decodes a 4000×3000 photo on the main thread.
          → decode a 200×200 thumbnail on a background thread; cache it.
Cause 2:  rows are created for all 2,000 items.
          → use a recycling list (RecyclerView / LazyColumn / List).
After:    frames 9 ms; scrolling smooth.
Accessibility: each row has a label "Photo from 12 March, 3 comments".
```

Measure first, move heavy work off the main thread, and draw only what is visible; label rows so screen-reader users get the same information.

> Key idea: Keep each frame within about 16 ms by moving work off the main thread, start quickly, let the system schedule background work, and make the app usable with a screen reader, large text and clear touch targets.

! Screen readers read the label aloud.

@solution
function backoff(attempt, baseMs, maxMs) {
  return Math.min(maxMs, baseMs * Math.pow(2, attempt));
}

function shouldRetry(status) {
  return status === 0 || status === 408 || status === 429 || (status >= 500 && status <= 599);
}

function migrationsToRun(current, target, available) {
  return available.filter((v) => v > current && v <= target).sort((x, y) => x - y);
}

function paginate(items, pageSize, cursor) {
  const start = cursor === null ? 0 : cursor;
  const end = start + pageSize;
  return { page: items.slice(start, end), next: end < items.length ? end : null };
}

function isFresh(storedAtMs, nowMs, maxAgeSeconds) {
  return nowMs - storedAtMs < maxAgeSeconds * 1000;
}

function compareVersions(a, b) {
  const pa = a.split(".").map(Number), pb = b.split(".").map(Number);
  const n = Math.max(pa.length, pb.length);
  for (let i = 0; i < n; i++) {
    const x = pa[i] || 0, y = pb[i] || 0;
    if (x < y) return -1;
    if (x > y) return 1;
  }
  return 0;
}

function inRollout(userId, percent) {
  return userId % 100 < percent;
}

function redact(record, keys) {
  const copy = Object.assign({}, record);
  for (const k of keys) {
    if (k in copy) copy[k] = "***";
  }
  return copy;
}

function deepLinkAllowed(url, hosts) {
  const prefix = "https://";
  if (!url.startsWith(prefix)) return false;
  const rest = url.slice(prefix.length);
  let end = rest.length;
  for (const ch of ["/", "?", "#"]) {
    const i = rest.indexOf(ch);
    if (i !== -1 && i < end) end = i;
  }
  const host = rest.slice(0, end);
  if (host.includes("@")) return false;
  return hosts.includes(host);
}

#LESSON Usability and design principles | 12
**Human-computer interaction** (HCI) studies how people use computer systems and how to design systems that people can use well. Software that is correct and fast still fails if its users cannot work out what to do.

### What usability means
The international standard defines usability by three measures, for specified users doing specified tasks:

- **Effectiveness:** can people complete the task, and accurately?
- **Efficiency:** how much time and effort does it take?
- **Satisfaction:** how do they feel about it?

The words "specified users" matter. An interface that suits an expert who uses it eight hours a day may be wrong for someone who uses it twice a year.

### Norman's principles
Donald Norman described what makes everyday things understandable:

- **Affordances:** what an object allows. A button affords pressing.
- **Signifiers:** the visible cues that show where to act. A raised, labelled shape says "press me". Flat text that is secretly a button has an affordance and no signifier.
- **Feedback:** every action produces an immediate, visible result.
- **Mapping:** the relation between controls and their effects is natural, such as a volume slider that goes up for louder.
- **Constraints:** the design prevents wrong actions, such as a greyed-out button.
- **Conceptual model:** the user can form an accurate picture of how the system works.

### Two gulfs
A user must bridge the **gulf of execution** (how do I do what I want?) and the **gulf of evaluation** (what happened, and was it what I wanted?). Good design narrows both: visible options for the first, clear feedback for the second.

### Nielsen's ten heuristics
A widely used checklist for judging an interface:

1. Visibility of system status.
2. Match between the system and the real world: the user's words, not the developer's.
3. User control and freedom: undo, cancel, a way out.
4. Consistency and standards.
5. Error prevention.
6. Recognition rather than recall: show options, do not make people remember.
7. Flexibility and efficiency: shortcuts for experts.
8. Aesthetic and minimalist design.
9. Help users recognise, diagnose and recover from errors.
10. Help and documentation.

### Errors are design problems
When people make mistakes, the design usually invited them. Distinguish **slips** (the right intention, the wrong action, such as tapping the neighbouring button) from **mistakes** (the wrong intention, from a wrong mental model). Prevent slips with spacing, confirmation of destructive actions and, above all, **undo**. Prevent mistakes with clearer models and language.

A good error message says what happened in plain words, why, and what to do next. "Error 0x80070057" does none of these.

### You are not the user
Designers and programmers know how the system works, so everything looks obvious to them. That knowledge cannot be switched off. The only way to learn whether a design works is to **watch real users try to use it**.

### Worked example
A heuristic evaluation of a checkout page against Nielsen's principles.

```text
Problem                                   Heuristic                     Severity
No progress indicator during payment      Visibility of system status   3
"Proceed" vs "Continue" mean different    Consistency and standards     2
Card error says "Error 402"               Help users recover from errors 4
Discount code field clears on error       User control and freedom      3
Fix first: the error message (severity 4) and the progress indicator.
```

Heuristics give a quick, cheap checklist; rating severity decides what to fix first.

> Key idea: Usability is effectiveness, efficiency and satisfaction for real users. Make actions visible, give feedback, prevent errors, and test with people who are not you.

#LESSON Human capabilities and limits | 13
Interfaces are used by human perception, memory and movement, which have measurable properties. Designing with them in mind is engineering, not taste.

### Perception
- **Visual hierarchy:** people scan, they do not read. Size, weight, colour and position tell the eye what matters. One primary action per screen should stand out.
- **Gestalt principles:** items that are close together (**proximity**) or look alike (**similarity**) are seen as a group. Spacing is therefore the main tool for showing structure.
- **Colour:** about one man in twelve has a colour-vision deficiency. Never use colour as the only signal; add an icon, a label or a shape.
- **Contrast:** text needs enough luminance contrast with its background. The Web Content Accessibility Guidelines require a ratio of at least **4.5:1** for normal text and 3:1 for large text.

### Attention
Attention is narrow. People miss changes outside the spot they are looking at (**change blindness**), so a message appearing at the far edge of the screen may never be seen. Put feedback near where the user acted. Interruptions are costly: after one, it takes time to resume.

### Memory
**Working memory** holds only a few items for a few seconds. Do not ask people to remember something from one screen to use on another. Show it. **Recognition** is much easier than **recall**, which is why menus beat command lines for occasional users.

People rely on **consistency** to avoid thinking: if "Save" is in the same place everywhere, it is found without a search.

### Fitts's law
The time to move to a target depends on its distance and size:

```text
T = a + b × log2(D / W + 1)
```

D is the distance to the target, W its width, and a and b are constants found by measurement. Consequences:

- Make frequent targets **large** and **near**.
- Screen edges and corners are easy to hit with a mouse, because the pointer stops there: they act as targets of unlimited depth.
- Tiny, distant close buttons are slow and error-prone.

### Hick's law
The time to decide among n equally likely choices grows with the logarithm of n:

```text
T = b × log2(n + 1)
```

More options mean slower decisions, but only logarithmically, and only when the options are organised. A long, well-ordered list can be faster than a deep tree of small menus. Group, order and highlight the commonest choices.

### Response time
Three thresholds are well established:

- **0.1 s:** feels instantaneous.
- **1 s:** the user notices the delay but keeps their train of thought.
- **10 s:** attention is lost. Show progress and allow cancelling.

For anything over a second, show that work is happening; for long operations, show how far it has got.

### Predicting performance
The **keystroke-level model** estimates how long an expert takes to do a task by adding standard times for each elementary operation: pressing a key (about 0.28 s), pointing with a mouse (1.1 s), moving a hand between keyboard and mouse (0.4 s), and mental preparation (1.35 s). It lets you compare two designs before building either.

### Human variety
Users differ in eyesight, hearing, dexterity, language, experience and context. Designing for the edges (one-handed use, bright sunlight, a screen reader) improves the design for everyone.

> Key idea: Human perception, memory and movement have known limits. Fitts's law and Hick's law turn "make it easy" into numbers.

* Working memory is small; recognising a shown option is far easier than remembering it

! Show the choices instead of making people remember them.

#LESSON The user-centred design process | 12
Good interfaces are not invented in one step. They are reached by a cycle: **understand** the users, **design**, **prototype**, **evaluate** with users, and repeat.

### Understand the users
Before designing, find out who the users are, what they are trying to achieve, and in what circumstances.

- **Interviews:** ask about what people did last time, not what they think they would do. People are poor at predicting their own behaviour.
- **Observation** (contextual inquiry): watch them do the work where it happens. You see the workarounds they no longer notice.
- **Surveys** for breadth, once you know the right questions.
- **Analytics** show what users do, never why.

Summarise the research so that the team can use it:

- A **persona** is a short description of a representative user, based on the research: goals, context, frustrations. It stops everyone designing for themselves.
- A **scenario** tells the story of a persona using the product to reach a goal.
- A **journey map** follows the steps and feelings across the whole experience and shows where it hurts.

### Define the problem
State what users need before proposing solutions. "Users need to know when their bus will arrive" is a need. "Add a map" is a solution, and perhaps not the best one.

### Prototype cheaply
A **prototype** is anything that lets you test an idea before building it.

- **Paper sketches:** minutes to make, and people criticise them freely because they are plainly unfinished.
- **Wireframes:** layout and structure without visual styling.
- **Interactive prototypes:** clickable mock-ups.

The cheaper the prototype, the more ideas you can try, and the earlier a bad one dies. Generate several different designs, not variations of one.

### Usability testing
Give representative users realistic **tasks** and watch.

- Ask them to **think aloud** as they work.
- Do **not help**. When they struggle, that is the finding.
- Record where they hesitate, go wrong and give up.
- Say clearly that the design is being tested, not them.

**Five users** find most of the serious problems in a design. It is better to test with five, fix, and test again with five more than to test once with fifteen.

Measure where useful: the **task success rate**, the time on task, the number of errors, and a satisfaction score.

### Iterate
Fix the most severe problems and test again. Each cycle should be short. A design tested weekly with paper beats one tested once, complete, after six months.

### In an agile team
Design work runs slightly ahead of development: research and prototypes for the next piece of work are tested while the current piece is being built, and what is built is tested in turn.

### Ethics of research
People who take part must give **informed consent**, may stop at any time, and must have their data protected and anonymised. Research with children or vulnerable people needs extra care and usually formal approval.

### Worked example
One cycle of user-centred design for a library booking app.

```text
Research:  5 interviews → students book rooms on their phones while walking.
Define:    "Book a free room in under 30 seconds, one-handed."
Ideate:    3 sketches; pick "nearest free room" as the first screen.
Prototype: clickable mock-up in a design tool.
Test:      5 students; 4 succeed; 1 confused by the time picker.
Iterate:   replace the time picker with "30 min / 1 h / 2 h" buttons; test again.
```

Short cycles of observing real users and changing the design catch problems before any code is written.

> Key idea: Understand users, prototype cheaply, test with real people, and iterate. Five users, thinking aloud, will find most of the serious problems.

! Helping hides the problem you came to find.

#LESSON Accessibility, evaluation and ethics | 12
### Accessibility
About one person in six has a significant disability, and everyone is sometimes limited: a broken wrist, bright sunlight, a noisy room. An accessible interface can be used by people who cannot see well or at all, cannot hear, cannot use a mouse, or process information differently.

The **Web Content Accessibility Guidelines** (WCAG) organise the requirements under four principles. Content must be:

- **Perceivable:** text alternatives for images, captions for video, sufficient contrast, content that survives being enlarged.
- **Operable:** everything works from the keyboard, focus is visible, nothing depends on precise timing, nothing flashes dangerously.
- **Understandable:** plain language, predictable behaviour, clear labels and error messages.
- **Robust:** correct, semantic markup that assistive technology can interpret.

Conformance has three levels: A, AA and AAA. **AA** is the usual legal and contractual target.

### Contrast, exactly
WCAG defines contrast from the **relative luminance** of the two colours:

```text
ratio = (L_lighter + 0.05) / (L_darker + 0.05)
```

The ratio runs from 1 (identical) to 21 (black on white). Level AA requires 4.5 for normal text and 3 for large text; AAA requires 7 and 4.5.

### Testing accessibility
- **Automated checkers** find missing labels and low contrast. They detect only a minority of real problems.
- **Keyboard only:** put the mouse away and try to complete the task.
- **A screen reader:** listen to your interface.
- **Zoom** to 200% and check that nothing is cut off.
- **People with disabilities** using their own equipment. Nothing replaces this.

Do not claim that a product is accessible on the strength of an automated scan.

### Evaluating without users
In a **heuristic evaluation**, several evaluators inspect the interface against a checklist such as Nielsen's heuristics and rate each problem's severity. It is quick and cheap, and finds different problems from user testing, so use both.

### Measuring satisfaction
The **System Usability Scale** (SUS) is a ten-statement questionnaire answered on a scale of 1 to 5. Odd-numbered statements are positive and even-numbered ones negative. To score it:

```text
odd items:  score − 1          even items:  5 − score
total × 2.5 gives a result from 0 to 100
```

The average across many systems is about **68**. A SUS score is not a percentage.

### Experiments
An **A/B test** shows two versions to randomly chosen groups of users and compares a measured outcome. Decide the measure and the sample size in advance, run the test to completion, and check that the difference is statistically significant. A/B tests say which version performed better, not why, and optimise only what you chose to measure.

### Ethics: dark patterns
Knowledge of human psychology can be used against users. **Dark patterns** are designs that trick people into choices they would not otherwise make:

- a subscription that takes one tap to start and a telephone call to cancel;
- a pre-ticked box for something the user did not ask for;
- "confirm-shaming" ("No thanks, I don't like saving money");
- false urgency ("only 2 left!") when it is not true;
- hiding the cost until the final step.

These damage trust and are increasingly unlawful. Design for the user's real goals, including the goal of leaving. Attention-maximising features (infinite feeds, constant notifications) deserve the same scrutiny: ask whether the product serves the user or exploits them.

> Key idea: Accessibility is measurable and testable, but only partly by tools. Evaluate with heuristics, measures and real users, and never use design to deceive.

#Q Which is a dark pattern?

#LESSON Forms, feedback and errors | 12
### Forms are conversations
Sign-up, checkout and settings screens are where users meet a system's demands most directly, and where many give up. A good form asks only what it needs, in the order a person expects, in plain language.

### Labels and inputs
- Every field needs a **visible label** that stays visible while typing. Placeholder text disappears as soon as you type, so it cannot replace a label, and it is often too faint to read.
- Put labels **above** fields on small screens so they are not cut off.
- Use the right **input type** so phones show the right keyboard: email, telephone, number, date.
- Group related fields, and mark which are **optional** rather than starring everything.
- Do not ask for the same information twice, and do not split one value, like a phone number, into several boxes.

### Validation and error messages
Check input at a sensible moment: when the user leaves a field or submits, not on every keystroke while they are still typing. When something is wrong:

- Say **what** went wrong and **how to fix it**: "Enter a date like 14/03/2026", not "Invalid input".
- Show the message **next to the field**, and also in a summary at the top for long forms.
- Do not rely on colour alone; add text or an icon, for colour-blind users and screen readers.
- Keep everything the user typed. Clearing a form on error is one of the most frustrating things software can do.

### Response time and feedback
Classic guidance from Nielsen sets three limits:

- About **0.1 seconds** feels instantaneous: no feedback needed beyond the result.
- About **1 second** keeps the user's train of thought, though they notice the delay.
- About **10 seconds** is the limit of attention; longer operations need a progress indicator and ideally a way to cancel.

Show a **determinate** progress bar when you know how much is left and a spinner only when you do not. Acknowledge every action immediately, even if the work continues in the background.

### Preventing and undoing errors
Prevention beats messages: disable a Pay button until required fields are valid, offer choices instead of free text where possible, and use sensible defaults.

For destructive actions, **undo** is usually better than a confirmation dialog. People learn to click "Yes, I'm sure" without reading, but an undo after the fact works every time. Keep confirmations for actions that truly cannot be undone, and make the button say what it does: "Delete 3 files", not "OK".

### Worked example
Rewriting a failing sign-up form.

```text
Before                                    After
Placeholder-only fields                   Visible labels above each field
Errors only after submit, at the top      Check each field when the user leaves it
"Invalid input"                           "Password needs at least 12 characters"
Form clears on error                      Everything typed is kept
Submit button always enabled              Button explains what is still missing
Result in testing: completion 61% → 88%.
```

Most form problems come from hidden instructions and unhelpful errors; fixing them is cheap and has a large effect.

> Key idea: Label every field visibly, validate at the right moment, and write errors that say how to fix the problem. Give feedback within the 0.1, 1 and 10 second limits, and prefer undo to "Are you sure?".

#LESSON Information architecture and navigation | 12
### Where things live
**Information architecture** (IA) is the organisation and labelling of content so people can find things and understand where they are. A product can have excellent screens and still fail if users cannot work out which menu holds the setting they need.

### Mental models
Users arrive with a **mental model**, their own idea of how things are grouped. Problems appear when the site is organised by the company's internal structure ("Departments", "Divisions") instead of by the user's tasks ("Pay a bill", "Report a problem"). Good IA starts from what people are trying to do and the words they use for it.

### Card sorting and tree testing
Two cheap research methods shape and check an IA:

- In **card sorting**, participants group cards, each naming a piece of content, into piles that make sense to them, and often name the piles. Open sorts let them invent groups; closed sorts use groups you supply. The results show which items people expect together and what they call the groups.
- In **tree testing**, participants see only the menu hierarchy, with no visual design, and are asked where they would look for something. The success rate and the paths taken show which labels mislead.

### Navigation patterns
- **Global navigation** (a top bar or tab bar) gives constant access to the main sections. On phones a bottom tab bar with three to five items is easy to reach with a thumb.
- **Local navigation** moves within a section.
- **Breadcrumbs** show the path from the home page and let users climb back up a level.
- **Search** suits large or unpredictable content and users who know exactly what they want; browsing suits people still exploring. Most sites need both.
- Hidden "hamburger" menus save space but reduce how often people use the items inside them. Keep the most important destinations visible.

### Wayfinding
At every moment users should be able to answer three questions: Where am I? Where can I go? How do I get back? Clear page titles, a highlighted current section, consistent placement of navigation, and predictable link text ("Billing settings" rather than "Click here") answer them.

### Labels
Labels are the most visible part of an IA. Use the users' words, keep them short and distinct, and avoid jargon and clever names. Two menu items whose meanings overlap ("Resources" and "Help") will send people to the wrong one half the time.

### Worked example
Reading the results of a tree test on a council website.

```text
Task: "Where would you report a broken streetlight?"
Expected path:  Home › Roads and transport › Report a problem
Success rate:   38%
Common wrong first click: "Contact us" (41%)
Change:         add "Report a problem" to the top-level menu and to "Contact us"
Re-test:        success rate 81%
```

Tree tests isolate the labels and structure, so a low success rate points directly at the menu, not the visual design.

> Key idea: Organise content around users' tasks and words, test the structure with card sorting and tree testing, and make sure every screen answers where am I, where can I go and how do I get back.

  return 0.2126 * ch[0] + 0.7152 * ch[1] + 0.0722 * ch[2];
}

function luminance(rgb) {
  return Math.round(rawLuminance(rgb) * 10000) / 10000;
}

function contrast(rgb1, rgb2) {
  const l1 = rawLuminance(rgb1), l2 = rawLuminance(rgb2);
  const hi = Math.max(l1, l2), lo = Math.min(l1, l2);
  return Math.round((hi + 0.05) / (lo + 0.05) * 100) / 100;
}

function wcagLevel(ratio, largeText) {
  const aaa = largeText ? 4.5 : 7, aa = largeText ? 3 : 4.5;
  if (ratio >= aaa) return "AAA";
  if (ratio >= aa) return "AA";
  return "fail";
}

function susScore(answers) {
  let total = 0;
  for (let i = 0; i < answers.length; i++) {
    total += i % 2 === 0 ? answers[i] - 1 : 5 - answers[i];
  }
  return total * 2.5;
}

function successRate(results) {
  if (results.length === 0) return 0;
  return Math.round(results.filter((r) => r).length / results.length * 100);
}

function klm(operators) {
  const times = { K: 0.28, P: 1.1, H: 0.4, M: 1.35, B: 0.1 };
  let total = 0;
  for (const op of operators) {
    total += times[op] || 0;
  }
  return Math.round(total * 100) / 100;
}
