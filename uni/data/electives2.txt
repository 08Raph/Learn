#LESSON Pixels, coordinates and rasterisation | 12
A screen is a grid of **pixels**, each storing a colour as red, green and blue intensities, usually 0 to 255 each. **Computer graphics** is the business of deciding the colour of every pixel, many times a second.

### Coordinates
Screen coordinates usually start at the **top-left**, with x growing to the right and y growing **downwards**. Mathematics and most 3D systems have y growing upwards, so a flip is needed somewhere, and getting it wrong draws the world upside down.

Objects are described in their own **local** coordinates, placed in the **world**, seen from a **camera**, and finally mapped to the **screen**. Each step is a change of coordinate system.

### The frame buffer
The image being built lives in memory as a **frame buffer**: one entry per pixel. To avoid showing a half-drawn picture, programs draw into a hidden **back buffer** and swap it with the visible one when the frame is complete (**double buffering**).

### Rasterisation
Shapes are described by geometry (a line between two points, a triangle with three corners). **Rasterisation** converts geometry into pixels.

**Lines.** Bresenham's algorithm steps along the longer axis one pixel at a time and decides, using only whole-number arithmetic, when to step on the other axis.

**Triangles.** Almost everything in real-time graphics is made of triangles, because three points always lie in one plane. To fill one, test each pixel in its bounding box: is the pixel's centre inside?

### Barycentric coordinates
Any point P inside a triangle ABC can be written as a weighted average of the corners:

```text
P = u·A + v·B + w·C      with   u + v + w = 1
```

The weights (u, v, w) are the **barycentric coordinates**. P is inside the triangle exactly when all three are between 0 and 1. They do double duty: the same weights **interpolate** any value stored at the corners, such as colour, depth or texture position, smoothly across the surface.

### Aliasing
Pixels are discrete, so slanted edges look like staircases (**aliasing**, or "jaggies"). **Anti-aliasing** softens them by letting a pixel that is partly covered take a blended colour, for example by sampling several points inside each pixel.

### Colour and blending
Colours are often stored with a fourth value, **alpha**, for opacity. Drawing a translucent colour over a background blends them:

```text
result = alpha × source + (1 − alpha) × background
```

This is linear interpolation, the most used operation in graphics.

> Key idea: Graphics turns geometry into pixel colours. Triangles, barycentric weights and interpolation do most of the work.
#Q When is a point inside a triangle, in terms of its barycentric coordinates?
- When their sum is zero
* When all three are between 0 and 1 (and they sum to 1)
- When exactly one is negative
! A negative weight means the point lies outside one of the edges.
#Q Why do programs draw to a back buffer and then swap?
- To use less memory
* So the viewer never sees a partly drawn frame
- To make colours brighter
! Double buffering shows only complete frames.

#LESSON Transformations and matrices | 13
Moving, turning and resizing objects are **transformations**. Graphics expresses every one of them as a matrix, so that they can be combined by multiplication and applied to thousands of points uniformly.

### The basic transformations in 2D
```text
scale by (sx, sy):      x' = sx·x            y' = sy·y
rotate by angle θ:      x' = x·cos θ − y·sin θ
                        y' = x·sin θ + y·cos θ
translate by (tx, ty):  x' = x + tx          y' = y + ty
```

Scaling and rotation are **linear**: they can be written as a 2 × 2 matrix. Translation cannot, because a matrix always leaves the origin where it is.

### Homogeneous coordinates
The fix is to add a third coordinate that is always 1, writing the point as (x, y, 1). Now translation is a matrix too:

```text
| 1  0  tx |   | x |   | x + tx |
| 0  1  ty | × | y | = | y + ty |
| 0  0  1  |   | 1 |   |   1    |
```

Every transformation is now a 3 × 3 matrix (4 × 4 in 3D), and a sequence of them **multiplies into a single matrix**. A model with a million points is transformed by one matrix, however many steps produced it.

### Order matters
Matrix multiplication is not commutative. "Rotate, then translate" spins an object in place and moves it. "Translate, then rotate" swings it round the origin in an arc. With column vectors, the matrix written **nearest the point is applied first**: `M = T · R` means rotate, then translate.

To rotate about a point other than the origin: translate that point to the origin, rotate, translate back.

### Hierarchies
A hand is attached to an arm attached to a body. Each part stores its transformation **relative to its parent**; its world transformation is the product down the chain. Move the body and everything attached follows. This is a **scene graph**, and it is how characters, vehicles and user interfaces are organised.

### Into three dimensions
3D adds a z axis and uses 4 × 4 matrices. Rotation becomes subtler: there are three axes, and combining rotations about them in sequence (Euler angles) can lose a degree of freedom, a failure called **gimbal lock**. Engines therefore store orientation as a **quaternion**, which interpolates smoothly and avoids the problem.

### Normals
A surface's **normal** is the direction it faces, needed for lighting. Normals are directions, not positions: they are not translated, and under non-uniform scaling they need the inverse transpose of the matrix to stay perpendicular.

> Key idea: Adding one coordinate turns every transformation into a matrix. Combining transformations is then multiplication, and the order decides the result.
#Q Why are homogeneous coordinates used?
- They make images sharper
* They let translation be expressed as a matrix, so all transformations combine by multiplication
- They remove the need for rotation
! A plain 2 × 2 matrix cannot move the origin.
#Q An object should spin in place and then be moved to its position. With column vectors, which matrix product does that?
* M = T · R (rotation applied first)
- M = R · T
- The order does not matter
! The matrix nearest the point acts first.

#LESSON The 3D pipeline: camera, projection and depth | 13
Drawing a 3D scene is a fixed sequence of steps, the **graphics pipeline**.

```diagram
   model coordinates
        |  model matrix        place the object in the world
   world coordinates
        |  view matrix         move the world so the camera is at the origin
   camera coordinates
        |  projection matrix   flatten 3D to 2D with perspective
   clip coordinates  --> divide by w -->  normalised device coordinates
        |  viewport transform
   screen pixels  -->  rasterise  -->  shade each pixel
```

### The camera
There is no camera object in the mathematics. Instead of moving a camera through the world, we apply the **inverse** transformation to the world, so that the camera sits at the origin looking down an axis. That is the **view matrix**.

### Perspective
Distant things look smaller. With the camera at the origin and a screen at distance d, similar triangles give:

```text
screen_x = d · x / z          screen_y = d · y / z
```

Dividing by depth is the whole of perspective. The projection matrix arranges for this division to happen (the "divide by w" step). An **orthographic** projection omits the division: sizes do not change with distance, as in engineering drawings and many 2D games.

The **field of view** is the angle the camera sees. The visible volume, a pyramid with its top cut off, is the **view frustum**, bounded by a **near** and a **far** plane.

### Clipping and culling
- **Clipping** discards or trims geometry outside the frustum.
- **Back-face culling** skips triangles that face away from the camera, which for a closed object is about half of them.
- **Frustum culling** skips whole objects outside the view, using a cheap bounding volume.

Not drawing something is the best optimisation there is.

### The depth buffer
When two surfaces cover the same pixel, the nearer one must win. The **depth buffer** (z-buffer) stores, for every pixel, the depth of the nearest surface drawn so far. A new fragment is kept only if it is nearer. Objects can then be drawn in any order.

Depth precision is finite and concentrated near the camera. Two surfaces very close together far away can flicker as rounding errors change the winner: **z-fighting**. Keeping the near plane as far out as you can helps.

Transparent surfaces are the exception: they must be drawn after the opaque ones, sorted from far to near, because blending depends on order.

### What runs where
The **vertex** stage transforms each corner of each triangle. The **rasteriser** finds the pixels each triangle covers and interpolates values across it. The **fragment** stage computes a colour for each of those pixels. On a modern GPU the vertex and fragment stages are small programs called **shaders**.

> Key idea: Model, view and projection matrices take a point from the object to the screen. Perspective is a division by depth, and the depth buffer sorts out what is in front.
#Q What produces the perspective effect that distant objects look smaller?
- Rotating the camera
* Dividing the x and y coordinates by the depth
- Increasing the resolution
! Similar triangles give screen position proportional to 1/z.
#Q What does the depth buffer store?
- The colour of each pixel
* For each pixel, the depth of the nearest surface drawn so far
- The list of triangles
! It lets surfaces be drawn in any order and still overlap correctly.

#LESSON Light, shading and textures | 13
Geometry gives shape. **Shading** gives the appearance: how bright and what colour each point looks, given the lights and the material.

### Diffuse reflection
A matte surface scatters light equally in all directions. How bright it looks depends only on the angle at which the light strikes it. **Lambert's law**:

```text
diffuse = max(0, N · L)
```

N is the unit surface normal and L the unit direction toward the light. Their dot product is the cosine of the angle between them: 1 when the light hits head on, 0 when it grazes the surface. The `max` stops surfaces facing away from the light going negative.

### Specular highlights
Shiny surfaces also reflect light in a preferred direction, producing a bright spot that moves as the viewer moves. The Phong and Blinn-Phong models add a term that is large when the viewer is near the mirror direction, raised to a power that controls how tight the highlight is.

### Ambient light
In reality light bounces between surfaces, so nothing is fully black. The simplest stand-in is a small constant **ambient** term. A complete basic model is:

```text
colour = ambient + diffuse × surface colour + specular
```

### Where shading is computed
- **Flat shading:** one colour per triangle. Faceted.
- **Gouraud shading:** compute lighting at the corners and interpolate the colours.
- **Phong shading:** interpolate the **normals** and light each pixel. Smooth, and the standard today.

### Textures
A **texture** is an image wrapped onto a surface. Each vertex carries **texture coordinates** (u, v) from 0 to 1 saying which part of the image it corresponds to. These are interpolated across the triangle with barycentric weights, and each pixel looks up its colour in the image.

When a texture is shown smaller than its true size, many texels fall in one pixel and the image shimmers. **Mipmaps**, a chain of pre-shrunk copies, fix that. **Filtering** blends neighbouring texels when magnified.

Textures carry more than colour. A **normal map** stores a direction per texel, faking fine surface detail under lighting without adding triangles.

### Shaders and the GPU
A **shader** is a small program run on the graphics processor: a **vertex shader** once per vertex, a **fragment shader** once per pixel covered. The GPU runs thousands of these in parallel, which is why it can light millions of pixels sixty times a second.

### Beyond the basics
**Physically based rendering** uses material properties (roughness, metalness) that behave consistently under any lighting. **Shadows** are commonly made by first rendering the scene's depth from the light's point of view. **Ray tracing** follows rays of light through the scene and handles reflections and soft shadows naturally, at much greater cost; recent hardware makes it practical in real time for some effects.

### Performance
Frame time goes to the number of **draw calls**, the number of triangles, and above all the number of **pixels shaded** (overdraw). Batch objects that share materials, cull what cannot be seen, and use simpler models for distant objects (**level of detail**).

> Key idea: Brightness of a matte surface is the dot product of its normal with the light direction. Textures and shaders add detail per pixel.
#Q Under Lambert's law, when is a surface brightest?
- When it faces away from the light
* When its normal points directly at the light
- When the viewer is close
! N · L is 1 when the two directions coincide.
#Q What problem do mipmaps solve?
- Slow vertex processing
* Shimmering when a texture is displayed much smaller than its original size
- Missing shadows
! A pre-shrunk copy matches the on-screen size.

#LESSON Colour, blending and anti-aliasing | 12
### Colour on a screen
Each pixel mixes red, green and blue light, usually stored as one byte per channel: 0 to 255. Graphics code often works with values from 0.0 to 1.0 instead, and converts at the end.

Those stored values are not proportional to light. Screens use the **sRGB** encoding, which spends more of the 256 steps on dark shades, where our eyes notice differences most. The value 128 is far less than half as bright as 255. This matters whenever you do arithmetic on colours: averaging, blending or lighting should happen in **linear** values, converted from sRGB first and back again at the end. Mixing in sRGB directly makes gradients look muddy and edges look too dark.

### Alpha and blending
A fourth channel, **alpha**, stores opacity: 1 is solid, 0 is invisible. Drawing a semi-transparent colour over what is already there uses the "over" operation:

```text
result = source · alpha + destination · (1 − alpha)
```

Order matters. Transparent objects must be drawn **after** solid ones and, among themselves, from back to front, or the blending is wrong. Engines sort transparent objects by distance for this reason, and still struggle when transparent objects overlap each other.

### Jagged edges
Rasterisation decides, for each pixel, whether a shape covers it. A sloping edge therefore becomes a staircase: **aliasing**. It is worst on thin lines and high-contrast edges, and it shimmers when the camera moves.

### Anti-aliasing
The fix is to estimate how much of each pixel the shape covers and blend accordingly.

- **Supersampling (SSAA)** renders at a higher resolution, for example four samples per pixel, and averages them. Excellent quality, four times the work.
- **Multisampling (MSAA)** takes several coverage samples per pixel at edges but shades the pixel only once. Most of the quality for much less cost.
- **Post-process methods (FXAA, SMAA)** find edges in the finished image and blur along them. Very cheap, slightly soft.
- **Temporal methods (TAA)** jitter the camera slightly each frame and blend with previous frames. Smooth, but can leave ghosting behind moving objects.

Textures alias too: shrinking a detailed texture onto a few pixels produces sparkle and moiré. **Mipmaps**, pre-shrunk copies of each texture at half, quarter and smaller sizes, let the renderer sample an appropriately blurred version.

> Key idea: Do colour arithmetic in linear light, draw transparent objects after solid ones from back to front, and fight aliasing by estimating coverage: supersampling, multisampling, post-processing or temporal methods, plus mipmaps for textures.
#Q Why should colours be converted from sRGB to linear values before blending or lighting?
- sRGB values are stored as text
* sRGB values are not proportional to light, so arithmetic on them gives wrong, too-dark results
- Linear values use less memory
! The encoding is perceptual; physics needs linear light.
#Q With the "over" operation, a red pixel with alpha 0.25 is drawn on white. How much of the result comes from the white background?
- 25%
* 75%
- 100%
! destination · (1 − alpha) = 0.75 of the background.
#Q What do mipmaps prevent?
- Z-fighting
* Sparkle and moiré when detailed textures are drawn small
- Slow loading of models
! They provide pre-filtered smaller versions of the texture.

#LESSON GPUs and shaders | 13
### Why graphics cards exist
A 1920 × 1080 frame has about two million pixels, and a game wants 60 or more frames a second. Each pixel needs similar but independent work. A **GPU** is built for exactly that: thousands of simple cores running the same program on different data at the same time. A CPU has a few powerful cores tuned for one complicated task at a time.

### Shaders
The programmable stages of the GPU pipeline run small programs called **shaders**, written in languages such as GLSL, HLSL, Metal Shading Language or WGSL.

- A **vertex shader** runs once per vertex. It applies the model, view and projection matrices from earlier lessons and passes values such as normals and texture coordinates onwards.
- The rasteriser then works out which pixels each triangle covers and **interpolates** the vertex outputs across the triangle.
- A **fragment (pixel) shader** runs once per covered pixel and returns its colour, usually by sampling textures and computing lighting.

```text
// GLSL fragment shader: simple diffuse lighting
in vec3 vNormal;
uniform vec3 lightDir;
uniform vec3 baseColour;
out vec4 colour;
void main() {
  float d = max(dot(normalize(vNormal), -lightDir), 0.0);
  colour = vec4(baseColour * d, 1.0);
}
```

**Uniforms** are values that are the same for every vertex or pixel in a draw, such as the light direction. Compute shaders run general calculations on the GPU, used for physics, particles and machine learning.

### Thinking in parallel
Shaders cannot see what neighbouring invocations are computing, and branches are expensive when neighbouring pixels take different paths, because groups of cores run in lock-step. Good shader code is straight-line arithmetic over its own inputs.

### Talking to the GPU
The CPU prepares data, uploads it to GPU memory, and issues **draw calls**. Each draw call has overhead, so engines **batch** many objects that share a material into one call and use **instancing** to draw thousands of copies of the same mesh with different positions. Moving data between CPU and GPU memory is slow; keep it on the GPU where possible.

### APIs
OpenGL and Direct3D 11 hide much of the hardware. Vulkan, Direct3D 12 and Metal give more control and less overhead in exchange for far more code. In the browser, **WebGL** and the newer **WebGPU** expose the GPU to JavaScript.

> Key idea: GPUs run the same small program over huge numbers of vertices and pixels in parallel. Vertex shaders transform, the rasteriser interpolates, and fragment shaders colour; keep draw calls few and data on the GPU.
#Q How often does a fragment (pixel) shader run?
- Once per frame
- Once per vertex
* Once for each pixel a triangle covers
! The rasteriser produces fragments; each gets its own invocation.
#Q What is a uniform in a shader?
- A value that differs for every pixel
* A value that is the same for every invocation in one draw call
- A type of texture
! Light directions and matrices are typical uniforms.
#Q Why do engines batch objects and use instancing?
- To make textures sharper
* To reduce the number of draw calls, each of which has CPU overhead
- To avoid writing shaders
! Fewer, larger draw calls keep the GPU busy and the CPU free.

Implement the mathematics of a tiny renderer. Points are `{ x, y }` (2D) or `{ x, y, z }` (3D). Matrices are arrays of rows.

- `matMul3(a, b)` multiplies two 3 × 3 matrices.
- `translate(tx, ty)` and `scale(sx, sy)` return 3 × 3 homogeneous matrices.
- `rotate90()` returns the matrix that rotates a point 90° anticlockwise about the origin (so (1, 0) becomes (0, 1)), using exact whole numbers.
- `apply(m, p)` transforms the 2D point `p` by the 3 × 3 matrix `m` and returns `{ x, y }`.
- `project(p, d)` perspective-projects a 3D point onto a screen at distance `d`: `{ x: d·x/z, y: d·y/z }`. Return `null` if `z` is 0 or negative (behind the camera).
- `barycentric(p, a, b, c)` returns `{ u, v, w }`, the barycentric coordinates of `p` in triangle `abc` (weights of `a`, `b` and `c`).
- `inTriangle(p, a, b, c)` returns true if `p` is inside or on the edge of the triangle.
- `lerpColor(c1, c2, t)` blends two colours `[r, g, b]`, rounding each channel to a whole number.
- `lambert(normal, light)` returns `max(0, N · L)` for two 3D **unit** vectors.

@solution
function matMul3(a, b) {
  const out = [];
  for (let i = 0; i < 3; i++) {
    const row = [];
    for (let j = 0; j < 3; j++) {
      row.push(a[i][0] * b[0][j] + a[i][1] * b[1][j] + a[i][2] * b[2][j]);
    }
    out.push(row);
  }
  return out;
}

function translate(tx, ty) {
  return [[1, 0, tx], [0, 1, ty], [0, 0, 1]];
}

function scale(sx, sy) {
  return [[sx, 0, 0], [0, sy, 0], [0, 0, 1]];
}

function rotate90() {
  return [[0, -1, 0], [1, 0, 0], [0, 0, 1]];
}

function apply(m, p) {
  return { x: m[0][0] * p.x + m[0][1] * p.y + m[0][2], y: m[1][0] * p.x + m[1][1] * p.y + m[1][2] };
}

function project(p, d) {
  if (p.z <= 0) return null;
  return { x: d * p.x / p.z, y: d * p.y / p.z };
}

function barycentric(p, a, b, c) {
  const det = (b.y - c.y) * (a.x - c.x) + (c.x - b.x) * (a.y - c.y);
  const u = ((b.y - c.y) * (p.x - c.x) + (c.x - b.x) * (p.y - c.y)) / det;
  const v = ((c.y - a.y) * (p.x - c.x) + (a.x - c.x) * (p.y - c.y)) / det;
  return { u, v, w: 1 - u - v };
}

function inTriangle(p, a, b, c) {
  const k = barycentric(p, a, b, c);
  return k.u >= 0 && k.v >= 0 && k.w >= 0;
}

function lerpColor(c1, c2, t) {
  return [0, 1, 2].map((i) => Math.round(c1[i] + (c2[i] - c1[i]) * t));
}

function lambert(normal, light) {
  return Math.max(0, normal.x * light.x + normal.y * light.y + normal.z * light.z);
}

#LESSON Decision making: state machines and behaviour trees | 12
**Game AI** is not machine learning. Its job is to make characters behave believably and to make the game fun, within a fraction of a millisecond per character. Mostly it is carefully organised rules.

### Finite state machines
The simplest useful structure. A guard is in one **state** at a time, and **events** move it between states.

```diagram
   patrol --(sees player)--> chase --(in range)--> attack
     ^                         |                      |
     +---(lost sight 5 s)------+<---(out of range)----+
```

Each state has behaviour while active, and optionally actions on entering and leaving. State machines are easy to write, to debug and to draw.

Their weakness is growth. With many states the transitions multiply, and behaviour shared between states ("flee when badly hurt, whatever you were doing") must be repeated everywhere. **Hierarchical** state machines group states so that a transition can be defined once on the group.

### Behaviour trees
The structure most commercial games use. A behaviour tree is evaluated from the root on every update. Each node returns **success**, **failure** or **running**.

- A **sequence** runs its children in order and fails as soon as one fails: "see the enemy AND have ammunition AND shoot".
- A **selector** tries its children in order and succeeds as soon as one succeeds: "attack, OR ELSE take cover, OR ELSE patrol". It encodes priorities.
- **Leaf** nodes are conditions and actions.
- **Decorators** modify one child: invert, repeat, limit by a timer.

Behaviours become reusable subtrees, and priorities are visible in the layout, which is why designers can edit them.

### Utility AI
Instead of fixed priorities, score every possible action by how useful it is right now (a function of health, distance, ammunition) and choose the best. Behaviour becomes graded and less predictable.

### Perception
A character should act on what it could plausibly know. Give it **senses**: a vision cone with a range and a line-of-sight test, hearing with a radius, and a memory of where the player was last seen. An enemy that always knows where you are feels unfair.

### Believability beats intelligence
Players need to **understand** what an enemy is doing. Characters announce their intentions, hesitate, and miss on purpose. A perfectly optimal opponent is usually not fun. Difficulty is tuned by reaction times, accuracy and aggression, not by making the AI smarter.

### Cost
AI shares the frame with everything else. Stagger updates so that not every character thinks on every frame, and give distant characters cheaper logic.

> Key idea: Game AI is structured decision making. State machines suit simple characters; behaviour trees scale by composing sequences (all must succeed) and selectors (first that succeeds).
#Q In a behaviour tree, what does a selector node do?
- Runs all its children at once
* Tries its children in order and succeeds as soon as one succeeds
- Always fails
! It expresses a list of alternatives in priority order.
#Q Why is a perfectly optimal game opponent usually undesirable?
- It uses too much memory
* Players need opponents that are understandable and beatable; fun matters more than strength
- It cannot be programmed
! Game AI serves the player's experience.

#LESSON Pathfinding | 13
A character must get from where it is to where it wants to be without walking through walls. **Pathfinding** treats the level as a graph and searches it.

### Representing the world
- A **grid:** each cell is walkable or blocked; neighbours are the adjacent cells. Simple, and wasteful for large open spaces.
- **Waypoints:** hand-placed nodes joined by edges.
- A **navigation mesh:** the walkable floor divided into convex polygons. A character can move freely inside a polygon, so far fewer nodes are needed. This is the standard in 3D games.

### Breadth-first search
On a grid where every step costs the same, **breadth-first search** explores outward in rings from the start and finds a shortest path. It explores in every direction equally, including directly away from the goal.

### Dijkstra's algorithm
When steps have different costs (mud is slower than road), always expand the node with the smallest total cost so far, using a priority queue. It finds the cheapest path and still searches in all directions.

### A*
A* adds a sense of direction. For each node it computes

```text
f = g + h
```

where **g** is the cost from the start and **h** is a **heuristic**: an estimate of the cost remaining to the goal. It expands the node with the smallest f, so it prefers nodes that are both cheap to reach and apparently close to the goal.

If h never **overestimates** the true remaining cost (it is **admissible**), A* is guaranteed to find a shortest path. Common heuristics:

- **Manhattan distance** |dx| + |dy| for grids with four-way movement.
- **Straight-line distance** when movement is unrestricted.

With h = 0, A* is Dijkstra's algorithm. A larger h explores less; one that overestimates is faster and no longer guaranteed optimal, a trade games sometimes make deliberately.

### After the path is found
Grid paths are jagged. **Smoothing** removes unnecessary corners by checking whether later points are directly reachable. Characters then follow the path with **steering behaviours**: seek the next point, arrive by slowing down, and avoid obstacles and each other.

### Many characters
Finding a path for each of a thousand units every frame is too slow.

- Spread requests over several frames.
- Share one **flow field** (a direction stored in every cell, pointing toward the goal) among all units heading to the same place.
- Use a **hierarchy**: plan between regions first, then within a region.
- Recompute only when the world changes.

### Dynamic worlds
Doors open and bridges fall. Paths are re-planned when blocked, and local avoidance handles moving obstacles that the planner did not know about.

> Key idea: A* searches by f = g + h. With a heuristic that never overestimates, it finds a shortest path while exploring far less than a blind search.
#Q In A*, what does h represent?
- The cost from the start to the node
* An estimate of the remaining cost from the node to the goal
- The number of nodes explored
! g is the known cost so far; h is the estimate ahead.
#Q What property of the heuristic guarantees that A* finds a shortest path?
- It is always zero
* It never overestimates the true remaining cost
- It is as large as possible
! Such a heuristic is called admissible.

#LESSON Physics: forces, impulses and collision response | 13
The foundation course detected collisions. This lesson makes objects **respond** like physical things.

### Newton's laws in code
An object has a position, a velocity and a **mass**. Forces cause acceleration:

```text
acceleration = force / mass
```

Each step: add up the forces (gravity, thrust, drag), compute the acceleration, update the velocity, then the position, using the semi-implicit Euler order. Heavier objects respond less to the same force, which is what makes them feel heavy.

A convenient trick is to store **inverse mass** (1/m). An immovable object such as a wall has inverse mass 0 and never moves, with no special cases.

### Impulses
A collision changes velocity almost instantly. Simulating the huge, brief forces is impractical, so physics engines apply an **impulse**: an immediate change in velocity.

When two objects collide along a **normal** direction n (pointing from one to the other), the speed at which they approach along the normal is

```text
v_rel = (v_b − v_a) · n
```

If it is positive they are already separating, and nothing is done. Otherwise the impulse magnitude is

```text
j = −(1 + e) · v_rel / (1/m_a + 1/m_b)
```

and the velocities change by j·n divided by each mass, in opposite directions. **Momentum is conserved**: what one object gains the other loses.

### Restitution
**e** is the **coefficient of restitution**, the bounciness, from 0 to 1.

- e = 1: perfectly elastic. The objects part at the speed they met.
- e = 0: perfectly inelastic. They do not bounce.

A ball dropped on the floor with e = 0.8 leaves at 80% of its arrival speed.

### Bouncing off a fixed surface
Against an immovable wall, the result simplifies to **reflection**:

```text
v' = v − (1 + e) · (v · n) · n
```

With e = 1 this is the mirror reflection used for a ball in Pong or Breakout.

### Positional correction
Because time advances in steps, objects are usually found already overlapping. As well as fixing velocities, push them apart along the normal by the penetration depth, shared according to inverse mass. Without this, objects sink slowly into the floor.

### Friction and drag
**Friction** opposes sliding along the surface and is proportional to how hard the surfaces are pressed together. **Drag** opposes motion through air or water; a simple model multiplies velocity by a factor slightly below 1 each step.

### Stability
Stacks of boxes jitter and springs explode when the time step is too large or varies. Use a fixed time step, solve contacts several times per step (**iterations**), and put objects that have come to rest to **sleep** so that they cost nothing.

### Use an engine for the hard part
Rotation, joints and continuous collision are intricate. Commercial games use established physics libraries. Knowing the principles lets you configure them and understand their artefacts.

> Key idea: Collisions are resolved with impulses along the contact normal. Restitution sets the bounce, inverse mass shares the effect, and momentum is conserved.
#Q What does a coefficient of restitution of 0 mean?
- A perfectly bouncy collision
* No bounce: the objects do not separate after impact
- No collision occurred
! The relative speed along the normal becomes zero.
#Q Why do physics engines store inverse mass?
- To save memory
* An immovable object has inverse mass 0, so it is handled by the same formulas with no special case
- Because mass cannot be measured
! Dividing by an infinite mass becomes multiplying by zero.

#LESSON Animation, feel and optimisation | 12
Two games with identical rules can feel completely different. The difference is in motion, feedback and smoothness.

### Interpolation
Almost all animation is **interpolation**: moving a value from a start to an end over time.

```text
lerp(a, b, t) = a + (b − a) · t          t runs from 0 to 1
```

Linear motion looks mechanical. **Easing functions** reshape t so that motion accelerates and decelerates:

```text
ease-in (quadratic):       t²                starts slowly
ease-out (quadratic):      1 − (1 − t)²      ends slowly
ease-in-out (smoothstep):  t² · (3 − 2t)     slow at both ends
```

A menu that eases into place, a camera that eases after the player: easing is everywhere in polished games. A **tween** is an object that drives a value from a to b over a duration with a chosen easing.

### Sprite animation
A 2D character animates by showing a sequence of frames from a **sprite sheet**. The frame to show is derived from **elapsed time**, never from a count of rendered frames, or the animation would run at different speeds on different machines:

```text
frame = floor(elapsed / frameDuration) mod frameCount
```

### Skeletal animation
3D characters are a mesh attached to a **skeleton** of bones. Animations store **keyframes**, the bone poses at chosen moments, and the engine interpolates between them. Animations are **blended** (walk into run) and layered (run while aiming). **Inverse kinematics** works backwards from where a hand or foot should be to the joint angles that put it there.

### Game feel
Small responses to the player's actions make a game satisfying:

- **Immediate response** to input. Delay of even a tenth of a second is felt.
- **Anticipation and follow-through:** a brief wind-up before a jump, a squash on landing.
- **Feedback:** a flash, a sound, particles, a few frames of screen shake on impact.
- **Forgiveness:** let the player jump for a moment after walking off a ledge ("coyote time"), and remember a jump pressed slightly too early (**input buffering**).

None of these change the rules. All of them change how the rules feel.

### Optimisation for real time
A frame at 60 frames a second has 16.7 ms for everything.

- **Measure first.** Profile to find whether the processor or the graphics card is the limit, and which system dominates.
- **Do less:** cull what is off screen; update distant objects less often; use simpler models far away.
- **Avoid allocation in the loop.** Creating objects every frame triggers garbage collection and visible hitches. Reuse them with an **object pool**.
- **Spatial partitioning** (grids, quadtrees) so that collision and queries look only at nearby objects.
- **Batching:** draw many objects that share a texture in one call.
- **Data layout:** keep the data a system loops over contiguous in memory.

Frame **consistency** matters as much as the average. One long frame in a hundred is seen as a stutter.

> Key idea: Derive animation from elapsed time, shape it with easing, respond to the player at once, and keep every frame inside its time budget.
#Q Why should the animation frame be computed from elapsed time and not from a frame counter?
- Time is easier to store
* So the animation plays at the same speed whatever the frame rate
- Frame counters overflow
! Counting rendered frames ties speed to the machine.
#Q What does an ease-out function do?
- Starts fast and stays fast
* Decelerates toward the end of the motion
- Reverses the motion
! Motion that settles gently looks natural.

#LESSON Steering behaviours and flocking | 12
### Movement that looks alive
Pathfinding decides where a character should go. **Steering behaviours**, described by Craig Reynolds in 1999, decide how it moves from moment to moment: speeding up, turning smoothly and avoiding others, instead of sliding along grid lines.

Each character has a position, a velocity, a maximum speed and a maximum force. A behaviour computes a **steering force**; the force changes the velocity a little each step, and the velocity changes the position. Limits on force and speed make the motion smooth, because nothing can turn instantly.

### The basic behaviours
- **Seek:** desired velocity points straight at the target at full speed. Steering = desired − current velocity. The character curves towards the target.
- **Flee:** the opposite of seek.
- **Arrive:** like seek, but inside a slowing radius the desired speed shrinks with distance, so the character stops at the target instead of overshooting and circling.
- **Pursue and evade:** seek or flee the target's **predicted** future position, not where it is now, which catches moving targets far better.
- **Wander:** small random changes to a steering target on a circle in front of the character, giving natural idle movement without jitter.
- **Obstacle avoidance:** look ahead along the velocity; if something is in the way, steer sideways.

### Combining behaviours
Real characters do several things at once: follow a path, avoid walls, keep away from each other. Their forces are **weighted and added**, or applied in priority order (avoid collisions first, then everything else) so that an urgent force is not cancelled by a calm one.

### Flocking
Reynolds' **boids** produce flocks, schools and crowds from three local rules, each looking only at nearby neighbours:

1. **Separation:** steer away from neighbours that are too close.
2. **Alignment:** steer towards the average heading of neighbours.
3. **Cohesion:** steer towards the average position of neighbours.

No boid knows about the flock as a whole, yet convincing group motion **emerges**. Tuning the three weights changes the character of the group from a tight school to a loose crowd.

### Keeping it fast
Checking every boid against every other is O(n²). A **spatial grid** or quadtree lets each boid examine only the cells around it, which makes thousands of agents practical.

### Worked example
One update step of the seek behaviour, with numbers.

```text
position (0, 0), velocity (1, 0), target (10, 10), maxSpeed 2, maxForce 0.5
desired  = normalise(target − position) × maxSpeed = (1.41, 1.41)
steering = desired − velocity                     = (0.41, 1.41)
limit to maxForce 0.5:  length 1.47 → scale → (0.14, 0.48)
velocity = (1, 0) + (0.14, 0.48) = (1.14, 0.48)
position = (0, 0) + velocity × dt(1)  = (1.14, 0.48)
```

Because the force is limited, the character curves gradually towards the target instead of snapping to face it.

> Key idea: Steering behaviours turn a goal into smooth motion by applying limited forces: seek, arrive, pursue, wander and avoid. Weighted together, and with separation, alignment and cohesion, they produce believable individuals and flocks.
#Q What does the arrive behaviour add to seek?
- Random wandering
* Slowing down within a radius so the character stops at the target instead of overshooting
- Prediction of the target's future position
! Desired speed shrinks as the distance shrinks.
#Q Why does pursue aim at a predicted position?
- It is cheaper to compute
* A moving target will have moved by the time the chaser arrives, so aiming ahead catches it sooner
- Prediction removes the need for a speed limit
! Seeking the current position leads to a tail chase.
#Q Which three rules produce flocking in Reynolds' boids?
- Seek, flee and wander
* Separation, alignment and cohesion
- Gravity, friction and collision
! Each rule looks only at nearby neighbours.

#LESSON Procedural generation and randomness | 12
### Content from algorithms
**Procedural generation** creates levels, terrain, loot or names with algorithms instead of by hand. It gives variety and replay value from a small download, but it needs careful design: random is not the same as interesting.

### Seeds
A pseudo-random generator started with the same **seed** produces the same sequence. Store the seed and you can regenerate a whole world from a single number, let players share worlds, and reproduce bugs. Use separate generators for separate systems (terrain, loot, enemies) so that a change in one does not reshuffle the others.

### Noise
Pure random values per tile give static, not landscapes. **Gradient noise** such as Perlin or simplex noise varies smoothly: nearby points have similar values. Adding several layers (**octaves**) at doubling frequency and halving strength gives detail at every scale, from mountains to pebbles. Height maps, clouds, textures and wind all use it.

### Simple generators worth knowing
- **Random walk:** a digger moves randomly, carving corridors.
- **Cellular automata:** fill a grid randomly, then repeatedly make each cell a wall if most of its neighbours are walls. A few steps turn noise into natural-looking caves.
- **Rooms and corridors:** place rooms that do not overlap, then connect them, for example with a minimum spanning tree plus a few extra links so there are loops.
- **Grammars and templates:** combine hand-made pieces by rules, which keeps quality high.

Always **validate** the result: is every room reachable (a breadth-first search answers that), is the exit not blocked, is the difficulty sensible? Regenerate if not.

### Randomness that feels fair
Players judge randomness by feel. A 10% drop chance can fail 30 times in a row, which feels broken.

- A **shuffle bag** puts outcomes in a bag, shuffles it, and draws without replacement, guaranteeing that each appears once per bag.
- **Pity timers** raise the chance after each failure.
- **Weighted random** picks items with different probabilities: draw a number from 0 to the total weight and walk through the items.

Never use the game's ordinary random generator for anything security-related, and disclose real odds when money is involved.

### Worked example
Generating a cave with a cellular automaton, step by step.

```text
1. Fill a 40×25 grid: each cell is wall with probability 0.45 (seed 1234).
2. Repeat 4 times: a cell becomes wall if 5 or more of its 8 neighbours are walls,
   otherwise floor.
3. Flood-fill from a floor cell; keep only the largest connected cave.
4. Validate: at least 40% floor; the exit is reachable by breadth-first search.
5. If validation fails, try the next seed.
```

A few lines of rules turn random noise into natural caves, and the validation step guarantees the level is playable.

> Key idea: Seeded generators make procedural content reproducible; smooth noise and simple algorithms build convincing worlds; validate what you generate; and shape randomness so it feels fair.
#Q Why store the seed of a procedurally generated level?
- It makes the level load faster
* The same seed regenerates exactly the same level, for sharing and debugging
- Seeds prevent cheating
! Same seed, same pseudo-random sequence, same level.
#Q What makes gradient noise better than independent random values for terrain?
- It is truly random
* Nearby points have similar values, so the result varies smoothly
- It is always zero at the edges
! Smoothness gives hills instead of static.
#Q A designer wants every item to appear once in every 10 drops. Which technique fits?
- A higher seed
* A shuffle bag
- Gradient noise
! Drawing without replacement guarantees each outcome once per bag.

@solution
function guardNext(state, event) {
  if (state === "patrol" && event === "see") return "chase";
  if (state === "chase" && event === "inRange") return "attack";
  if (state === "attack" && event === "outOfRange") return "chase";
  if ((state === "chase" || state === "attack") && event === "lost") return "patrol";
  return state;
}

function selector(children) {
  for (const child of children) {
    if (child()) return true;
  }
  return false;
}

function sequence(children) {
  for (const child of children) {
    if (!child()) return false;
  }
  return true;
}

function manhattan(a, b) {
  return Math.abs(a[0] - b[0]) + Math.abs(a[1] - b[1]);
}

function shortestPath(grid, start, goal) {
  const rows = grid.length, cols = rows ? grid[0].length : 0;
  const free = (r, c) => r >= 0 && c >= 0 && r < rows && c < cols && grid[r][c] !== "#";
  if (!free(start[0], start[1]) || !free(goal[0], goal[1])) return -1;
  const dist = new Map();
  dist.set(start[0] + "," + start[1], 0);
  const queue = [start];
  let head = 0;
  while (head < queue.length) {
    const [r, c] = queue[head++];
    const d = dist.get(r + "," + c);
    if (r === goal[0] && c === goal[1]) return d;
    for (const [dr, dc] of [[1, 0], [-1, 0], [0, 1], [0, -1]]) {
      const nr = r + dr, nc = c + dc, key = nr + "," + nc;
      if (free(nr, nc) && !dist.has(key)) {
        dist.set(key, d + 1);
        queue.push([nr, nc]);
      }
    }
  }
  return -1;
}

function reflect(v, n, e) {
  const dot = v.x * n.x + v.y * n.y;
  if (dot > 0) return v;
  return { x: v.x - (1 + e) * dot * n.x, y: v.y - (1 + e) * dot * n.y };
}

function clamp01(t) {
  return Math.max(0, Math.min(1, t));
}

function easeOut(t) {
  const x = clamp01(t);
  return 1 - (1 - x) * (1 - x);
}

function smoothstep(t) {
  const x = clamp01(t);
  return x * x * (3 - 2 * x);
}

function spriteFrame(elapsedMs, frameMs, count) {
  return Math.floor(elapsedMs / frameMs) % count;
}

#LESSON Microcontrollers and memory-mapped hardware | 12
A desktop processor is one part of a computer that also needs memory chips, storage and many supporting parts. A **microcontroller** puts a small processor, memory and input/output hardware on **one chip**, costing from under a dollar. Microcontrollers are inside washing machines, cars, toys, thermostats and medical devices: billions are made every year. Software written for them is **embedded software**, or **firmware**.

### What is on the chip
- A **CPU**, often 32-bit, running at tens of megahertz.
- **Flash memory** for the program: tens of kilobytes to a few megabytes. It keeps its contents without power.
- **RAM** for variables: often only a few kilobytes.
- **Peripherals:** general-purpose input/output pins, timers, analogue-to-digital converters, serial interfaces.

Resources are thousands of times smaller than a laptop's. There is usually no operating system, no file system and no screen.

### Registers control the hardware
How does software switch on a pin? Each peripheral is controlled by **registers** that appear at fixed **memory addresses**. Writing a number to that address changes what the hardware does. This is **memory-mapped I/O**.

```c
#define GPIO_OUT (*(volatile unsigned int *)0x40020014)

GPIO_OUT |= (1u << 5);       // set bit 5: pin 5 goes high, the LED lights
GPIO_OUT &= ~(1u << 5);      // clear bit 5: pin 5 goes low
```

`volatile` tells the compiler that the value can change outside the program's control, so it must really read and write it every time.

### Bit manipulation
A register packs many settings into one number, one or a few bits each. Four operations are used constantly:

```text
set bit n:      reg |=  (1 << n)
clear bit n:    reg &= ~(1 << n)
toggle bit n:   reg ^=  (1 << n)
test bit n:     (reg >> n) & 1
```

Always change only the bits you mean to, leaving the others as they were: read the register, modify, write back.

### General-purpose I/O
A **GPIO** pin can be configured as an **output** (the program drives it high or low) or an **input** (the program reads whether the outside world is driving it high or low). Typically one register sets the direction, one writes outputs and one reads inputs.

### The datasheet
Each chip's registers, addresses and bit meanings are defined in its **datasheet** and reference manual, which run to hundreds of pages. Reading them carefully is a central skill of embedded work.

### No safety net
There is no operating system to catch a bad pointer. A bug can lock the device until someone presses reset. Products therefore use a **watchdog timer**: a hardware counter that resets the chip unless the program regularly "kicks" it, so a hung program recovers by itself.

> Key idea: In embedded systems, hardware is controlled by writing bits to registers at fixed memory addresses.
#Q What is memory-mapped I/O?
- Storing files in RAM
* Controlling hardware by reading and writing registers that appear at memory addresses
- A kind of network protocol
! The peripheral responds to writes at its address.
#Q Which expression clears bit 3 of `reg` and leaves the other bits unchanged?
- reg |= (1 << 3)
* reg &= ~(1 << 3)
- reg = 0
! AND with a mask that has only bit 3 at zero.

#LESSON Basic electronics for programmers | 13
Embedded software exists to control electricity. You need a little circuit theory to avoid destroying the hardware and to understand why your code does not work.

### Voltage, current and resistance
- **Voltage** (V, volts) is electrical pressure: the push that moves charge.
- **Current** (I, amperes) is the flow of charge.
- **Resistance** (R, ohms, Ω) opposes the flow.

**Ohm's law** relates them:

```text
V = I × R          I = V / R          R = V / I
```

**Power** dissipated as heat is P = V × I, in watts.

### Lighting an LED safely
An LED needs a certain **forward voltage** (about 2 V for red) and must have its current limited (typically 5 to 20 mA), or it burns out. A **resistor** in series does that. From a 3.3 V pin, for 10 mA:

```text
R = (supply − forward voltage) / current = (3.3 − 2.0) / 0.010 = 130 Ω
```

Choose the next standard value above. A GPIO pin itself can supply only a few milliamps; anything larger, such as a motor, must be switched through a **transistor**.

### Logic levels
Digital pins interpret a voltage near the supply as 1 and near zero as 0. Microcontrollers commonly run at 3.3 V; older parts use 5 V. Connecting a 5 V output to a 3.3 V input can damage it. Always check.

### Floating inputs and pull-ups
An input connected to nothing **floats**: it picks up electrical noise and reads randomly. A **pull-up resistor** connects the pin weakly to the supply, so that it reads 1 unless something actively pulls it to 0. A button is then wired between the pin and ground: pressed reads 0, released reads 1. Most microcontrollers have pull-ups built in that software can switch on.

### The voltage divider
Two resistors in series divide a voltage:

```text
V_out = V_in × R2 / (R1 + R2)
```

It is used to scale a voltage down to a safe range and to read resistive sensors, such as a thermistor whose resistance changes with temperature.

### Analogue and digital
The physical world is **analogue**: temperature and light vary continuously. An **analogue-to-digital converter** (ADC) measures a voltage and returns a number. A 10-bit converter with a 3.3 V reference returns 0 to 1023:

```text
voltage = reading × 3.3 / 1023
```

### Switch bounce
A mechanical button does not close cleanly. Its contacts bounce for a few milliseconds, producing a burst of on-off transitions. Software that reacts to each one counts a single press many times. **Debouncing** accepts a change only after the input has been stable for a short period.

### Decoupling and noise
Digital chips draw current in sharp bursts, which disturbs the supply. Small **capacitors** placed beside each chip smooth it. Noise problems look like random software bugs, which is why hardware and software must be debugged together, with a **multimeter** and an **oscilloscope** as well as a debugger.

> Key idea: V = I × R. Limit current with a resistor, never leave an input floating, and expect buttons to bounce.

- 200 Ω
* 300 Ω
- 500 Ω
! (5 − 2) / 0.010 = 300.
#Q Why is a pull-up resistor used on a button input?
- To make the button brighter
* To give the input a defined level when the button is not pressed
- To increase the current
! A floating input reads noise.

#LESSON Timers, interrupts, PWM and analogue input | 13
### The problem with waiting
A naive program waits in a loop for a button to be pressed, doing nothing else. Meanwhile it cannot read a sensor or update a display. Two hardware features solve this.

### Interrupts
An **interrupt** is a signal from hardware that makes the processor **suspend what it is doing**, run a short function called an **interrupt service routine** (ISR), and then resume exactly where it left off.

```diagram
   main program ----------+              +-------- continues
                          | interrupt    |
                          v              |
                        [ ISR runs ] ----+
```

Sources include a pin changing, a timer expiring, a byte arriving on a serial port, or a conversion finishing.

Rules for ISRs:

- **Keep them short.** Set a flag or store a value, and let the main loop do the work.
- **Shared data is dangerous.** If the ISR and the main program both use a variable, an interrupt can arrive halfway through an update. Mark the variable `volatile` and briefly disable interrupts round multi-step accesses.
- Do not call slow functions inside one.

This is a race condition, exactly as with threads, and the remedy, protecting the critical section, is the same.

### Timers
A **timer** is a hardware counter driven by the clock. It can raise an interrupt at a regular interval, giving the program a reliable heartbeat, measure the length of a pulse, or generate output signals. Timing derived from a timer does not drift when the code changes; timing from delay loops does.

The interval follows from the clock frequency, a **prescaler** that divides it, and the count at which the timer resets:

```text
interval = prescaler × (reload + 1) / clock frequency
```

### Pulse-width modulation
A digital pin is on or off. To dim an LED or control a motor's speed, switch it on and off very fast and vary the proportion of time it is on: the **duty cycle**.

```diagram
   25% duty:   ‾|___|‾|___|‾|___       average = 25% of the supply
   75% duty:   ‾‾‾|_|‾‾‾|_|‾‾‾|_       average = 75% of the supply
```

At a high enough frequency the load responds to the average. A timer generates **PWM** in hardware with no effort from the program. Servo motors read the pulse width itself as a position command.

### Analogue input in practice
Reading an ADC takes time and the result is noisy. Common practice: take several readings and average them, or apply a simple filter. Resolution limits what you can distinguish: a 10-bit converter on 3.3 V has steps of about 3.2 mV.

### Polling or interrupts
**Polling** checks a device repeatedly in the main loop: simple, and fine for slow things. **Interrupts** respond immediately and let the processor **sleep** in between, which matters greatly for battery life. Most firmware mixes the two.

### Low power
A device may need to run for years on a coin cell. The processor spends almost all its time in a **sleep mode** drawing microamps, waking on a timer or an external event, doing its work in milliseconds, and sleeping again. The average current, and so the battery life, is set by how short the awake periods are.

> Key idea: Interrupts let hardware get the processor's attention at once. Keep service routines tiny, protect shared data, and use timers for anything that depends on time.

* As little as possible, such as setting a flag for the main loop
- Wait for user input
! Long ISRs delay other interrupts and the main program.

* 2 V
- 5 V
! 40% of 5 V.

#LESSON Serial buses and firmware structure | 13
A microcontroller talks to sensors, displays, radios and other chips over **serial buses**, which send one bit at a time down a few wires.

### UART
Two wires, transmit and receive, with **no shared clock**. Both ends agree a speed in advance, the **baud rate**. Each byte is framed: a **start bit** (0), eight data bits with the least significant first, an optional **parity** bit, and a **stop bit** (1).

```diagram
   idle ‾‾‾|_| d0 d1 d2 d3 d4 d5 d6 d7 |‾| idle
          start        data          stop
```

Simple and universal: it is how boards print debug messages to a computer. It connects exactly two devices, and both must agree on the speed.

### I²C
Two wires shared by many devices: a clock line and a data line. One **controller** drives the clock and addresses each **peripheral** by a 7-bit address, and the peripheral **acknowledges** each byte. Few wires, many devices, moderate speed. Common for sensors.

### SPI
Four wires: clock, data out, data in, and a separate **chip-select** line per device. No addressing and no acknowledgement, but simple and fast. Common for displays, memory cards and fast sensors.

| | Wires | Devices | Speed | Typical use |
|---|---|---|---|---|
| UART | 2 | 2 | Low to medium | Debug output, modules |
| I²C | 2 | Many, by address | Medium | Sensors |
| SPI | 3 + 1 per device | Several | High | Displays, storage |

In cars, **CAN** adds robust error handling and priorities. Wireless links (Bluetooth Low Energy, Wi-Fi) are usually a separate module spoken to over one of the buses above.

### Checking the data
Wires pick up noise. Protocols add a **parity bit**, a **checksum** or a **CRC**, so that corrupted data is detected and discarded or requested again.

### How firmware is organised
**The super-loop.** The simplest structure:

```c
int main(void) {
    setup();
    while (1) {
        read_inputs();
        update_state();
        write_outputs();
    }
}
```

Each function must return quickly. Nothing may block, or everything else stops.

**State machines.** Because nothing may wait, each activity is written as a state machine that advances a little on every pass: a button's debounce, a communication protocol, a heating cycle. This is the dominant style in small firmware.

**A real-time operating system** (RTOS) provides tasks with priorities, a scheduler, queues and timers. It suits larger firmware with several independent activities and deadlines, at the cost of memory and of the usual concurrency hazards.

### Real time
A **real-time** system must respond within a **deadline**. It is about predictability, not speed. In a **hard** real-time system (an airbag, a motor controller) a missed deadline is a failure. Designers analyse the **worst-case** execution time, avoid dynamic memory allocation because its timing is unpredictable, and keep interrupts short.

### Development practice
- Code is **cross-compiled** on a computer and **flashed** onto the chip.
- A **debug probe** lets you set breakpoints on the real hardware.
- A **hardware abstraction layer** separates the logic from the registers, so the logic can be **unit tested on a computer**.
- Updates in the field need a **bootloader** and a safe update procedure that survives power loss halfway.
- Embedded devices are attacked too: sign firmware, disable debug ports in production, and never ship default passwords.

> Key idea: UART, I²C and SPI trade wires, speed and device count. Firmware is a loop of non-blocking state machines, and real time means meeting deadlines predictably.
#Q Which bus addresses many devices over only two shared wires?
- UART
* I²C
- SPI
! Each peripheral has an address on the shared bus.
#Q What defines a hard real-time system?
- It is very fast
* Missing a deadline counts as a failure of the system
- It uses a large processor
! Predictability, not raw speed, is the requirement.

#LESSON Power, sleep and battery life | 12
### Every microamp counts
A sensor that must run for two years on a coin cell cannot keep its processor awake. Embedded programmers think about **current** (in milliamps, mA, or microamps, µA) as carefully as about speed.

Battery capacity is given in **milliamp-hours** (mAh). A 220 mAh coin cell can, in theory, supply 1 mA for 220 hours, or 10 µA for 22,000 hours (about 2.5 years). Real capacity is lower at high currents and in the cold, so designers keep a safety margin.

### Duty cycling
Most devices spend almost all their time doing nothing. The trick is to be **asleep** then. If a device draws 5 mA for 20 ms every 10 seconds and 4 µA the rest of the time, its average current is:

```text
average = 5 mA × (0.02 / 10) + 0.004 mA × (9.98 / 10)
        ≈ 0.010 mA + 0.004 mA = 0.014 mA
```

At 14 µA the coin cell lasts around 220 / 0.014 ≈ 15,700 hours, almost 1.8 years. Notice that the sleep current matters as much as the active current: halving sleep current here buys far more than speeding up the active part.

### Sleep modes and waking up
Microcontrollers offer several sleep levels. Light sleep stops the processor clock but keeps peripherals and memory running; deep sleep turns off almost everything and may lose the contents of RAM. The device wakes on an **interrupt**: a timer, a button press, or data arriving on a bus. Polling in a busy loop (`while (!ready) {}`) keeps the processor awake and is the classic battery killer.

### Other power drains
- **Radios** are usually the biggest consumer. Send less often, send less data, and batch transmissions.
- **LEDs** draw several milliamps each: blink briefly instead of staying on.
- **Pull-up resistors** on inputs that are held low waste current continuously.
- Unused peripherals and floating pins should be disabled or tied to a defined level.
- **Voltage regulators** have their own quiescent current; pick low-power ones.

### Measuring
Estimate on paper, then measure: a current meter or power profiler shows the spikes and the sleep floor. Many products ship with a surprise in the sleep current that only measurement reveals.

> Key idea: Battery life is capacity divided by average current. Keep the device asleep, wake by interrupt rather than polling, minimise radio use, and measure the real sleep current.

- 1,000 hours
! 1000 / 0.05 = 20,000 hours.
#Q Why is a busy-wait loop like while (!ready) {} bad in a battery-powered device?

#Q In a duty-cycled device that is asleep 99.8% of the time, what often dominates battery life?

! Small currents over long times add up.

#LESSON Debugging and testing embedded systems | 13
### Why it is harder
Embedded code runs on a device with no screen, little memory, real-time deadlines and hardware that can itself be faulty. A bug might be in your code, the wiring, a component, or the timing between them.

### Simple tools first
- **An LED** is the embedded "hello world" and the first debugging tool: blink a pattern to show which state the program reached.
- **Serial output** over a UART to a computer is the equivalent of print statements. Keep messages short: printing is slow and can change the timing you are trying to observe.
- **Asserts** that halt and report the file and line catch impossible states early.

### Instruments
- A **multimeter** checks voltages, continuity and current: is the chip powered at all?
- A **logic analyser** records many digital signals over time and decodes protocols such as UART, I2C and SPI, so you can see exactly which bytes were sent and when.
- An **oscilloscope** shows the real analogue shape of a signal: slow edges, noise, ringing or a supply voltage dipping when a motor starts.

### Debug probes
Most microcontrollers have a debug port (**JTAG** or **SWD**). With a probe and a debugger such as GDB you can set breakpoints, step through code, and read memory and registers on the running chip. Remember that stopping at a breakpoint also stops the program's timing: motors keep moving and communication partners time out.

### Defending against the unexpected
- A **watchdog timer** resets the device if the program stops "feeding" it, recovering from hangs in the field.
- Log the **reset reason** at start-up (power-on, watchdog, brown-out) to learn what happened.
- Check stack usage: stack overflows are a common, silent cause of corruption on small devices.

### Testing
- **Unit-test on the host:** keep hardware access behind small interfaces so the logic can be compiled and tested on a normal computer with fake hardware. Most bugs are in logic, and this finds them fast.
- **Hardware-in-the-loop (HIL)** tests run the real firmware on a real board, with a test rig that drives inputs and checks outputs automatically.
- **Soak tests** run for days to find leaks and rare timing bugs.
- Test the edges: low battery, brown-outs, unplugged sensors and corrupt messages.

### Worked example
A sensor board resets randomly about once a day. A debugging plan:

```text
1. Log the reset reason at boot over UART:  "reset: WATCHDOG"
2. Hypothesis: a task blocks too long. Add timestamps around each task.
3. Finding: the I2C read occasionally hangs for 3 s when the sensor is unplugged.
4. Fix: add a 50 ms I2C timeout and retry; feed the watchdog only from the main loop.
5. Verify: a hardware-in-the-loop rig unplugs the sensor 500 times; no resets.
6. Unit-test the retry logic on the host with a fake I2C bus.
```

Recording why the device reset turns a mystery into a lead, and an automated rig proves the fix under the exact condition that failed.

> Key idea: Start with LEDs, serial output and asserts; use a logic analyser and oscilloscope to see the signals; use a debug probe with care for timing; protect with a watchdog; and test logic on the host before testing on hardware.

function setBit(reg, n) {
  return (reg | (1 << n)) >>> 0;
}

function clearBit(reg, n) {
  return (reg & ~(1 << n)) >>> 0;
}

function toggleBit(reg, n) {
  return (reg ^ (1 << n)) >>> 0;
}

function readBit(reg, n) {
  return (reg >>> n) & 1;
}

function writeField(reg, shift, width, value) {
  const mask = ((1 << width) - 1) << shift;
  return ((reg & ~mask) | ((value << shift) & mask)) >>> 0;
}

function ledResistor(supply, forward, milliamps) {
  return Math.round((supply - forward) / (milliamps / 1000));
}

function divider(vin, r1, r2) {
  return Math.round(vin * r2 / (r1 + r2) * 1000) / 1000;
}

function adcToVolts(reading, bits, vref) {
  return Math.round(reading * vref / (Math.pow(2, bits) - 1) * 1000) / 1000;
}

function pwmAverage(supply, dutyPercent) {
  return Math.round(supply * dutyPercent / 100 * 100) / 100;
}

function timerInterval(clockHz, prescaler, reload) {
  return prescaler * (reload + 1) / clockHz * 1000;
}

function debounce(samples, needed) {
  const out = [];
  if (samples.length === 0) return out;
  let state = samples[0], run = 0;
  for (const s of samples) {
    if (s === state) {
      run = 0;
    } else {
      run++;
      if (run >= needed) { state = s; run = 0; }
    }
    out.push(state);
  }
  return out;
}

function uartFrame(byte, parity) {
  const bits = [0];
  let ones = 0;
  for (let i = 0; i < 8; i++) {
    const b = (byte >> i) & 1;
    bits.push(b);
    ones += b;
  }
  if (parity === "even") bits.push(ones % 2);
  bits.push(1);
  return bits;
}

#LESSON Memory technologies and addressing | 12
Programs see memory as one long array of bytes. Underneath are several technologies with very different speed, cost and behaviour, arranged so that the common case is fast.

### Volatile memory
- **SRAM** holds each bit in a small circuit of about six transistors. Very fast, expensive and bulky. Used for processor caches.
- **DRAM** holds each bit as charge on a tiny capacitor with one transistor. Dense and cheap, but the charge leaks, so every cell is **refreshed** many times a second. Used for main memory.

Both forget everything when power is removed.

### Non-volatile memory
- **Flash** traps charge in an insulated gate and keeps it for years without power. It can be read quickly, but it must be **erased in whole blocks** before being rewritten, and each block survives only a limited number of erase cycles.
- **ROM** and one-time-programmable memory hold fixed code.
- **EEPROM** allows small amounts of data to be rewritten byte by byte.

### The hierarchy
```diagram
   registers    <1 ns      bytes
   cache        1–15 ns    KB to MB
   main memory  ~100 ns    GB
   solid state  ~100 µs    hundreds of GB
   hard disk    ~10 ms     TB
```

Each level is larger, cheaper per byte and slower than the one above. Because programs reuse the same data and nearby data, keeping recent items in the fast levels makes the whole behave almost as fast as the top and almost as large as the bottom.

### Addresses
Every byte has an **address**. With n address bits a processor can address 2ⁿ bytes: 32 bits reach 4 GB; 64-bit systems reach far more than any machine holds.

Data larger than a byte occupies several consecutive addresses. Many processors require or prefer **alignment**: a 4-byte value at an address divisible by 4. Compilers insert **padding** into structures to achieve it, which is why reordering fields can shrink a structure.

### Endianness
The number 0x12345678 needs four bytes. In which order?

```text
address:        0     1     2     3
big-endian:     12    34    56    78      most significant byte first
little-endian:  78    56    34    12      least significant byte first
```

x86 and most ARM systems are **little-endian**. Network protocols are **big-endian** ("network byte order"). Whenever binary data crosses between machines, in a file or on a network, the byte order must be defined and converted, or 1 becomes 16,777,216.

### Paging, briefly
An operating system divides memory into **pages**, typically 4 KB. A virtual address splits into a **page number** and an **offset** within the page; the page number is translated to a physical frame and the offset is kept. With 4 KB pages the low 12 bits are the offset.

### Memory errors
Cosmic rays and electrical noise occasionally flip a bit. Servers use **ECC memory**, which stores extra check bits to correct single-bit errors and detect double ones. Storage devices use much stronger codes.

> Key idea: Memory is a hierarchy of technologies trading speed for cost. Multi-byte values have a byte order that must be agreed whenever data leaves the machine.
#Q Why must DRAM be refreshed?
- To update the software
* Each bit is stored as charge on a capacitor that leaks away
- To cool it down
! Refresh rewrites every cell before the charge is lost.
#Q The 16-bit value 0x1234 is stored little-endian at address 100. What is at address 100?
- 0x12
* 0x34
- 0x00
! The least significant byte comes first.

#LESSON Storage devices and file systems | 12
Storage keeps data when the power is off. Its characteristics shape how databases and operating systems are designed.

### Hard disk drives
Spinning magnetic platters with a head on a moving arm. To read a block the arm must **seek** to the right track and wait for the disk to **rotate** to the right place: around 10 milliseconds, an eternity for a processor. Reading consecutive blocks afterwards is fast. Disks are therefore good at **sequential** access and very poor at **random** access, a fact that shaped decades of software design. They remain the cheapest storage per terabyte.

### Solid-state drives
Flash memory with no moving parts. Random reads take about a tenth of a millisecond, a hundred times better than a disk. Flash has awkward rules, however:

- It is read and written in **pages** (a few kilobytes) but erased only in much larger **blocks**.
- A page cannot be overwritten; the block must be erased first.
- Each block wears out after a limited number of erases.

A controller inside the drive hides this with a **flash translation layer**. It writes new data to fresh pages, remaps addresses, **garbage-collects** blocks of stale pages in the background, and spreads erases evenly over the device (**wear levelling**). Writing can cause more physical writes than were requested: **write amplification**.

### Blocks
Both kinds of device present themselves as an array of fixed-size **blocks**, read and written whole. Everything above is built on that.

### File systems
A **file system** turns blocks into named files in directories. It records, for each file, its size, permissions, timestamps and **which blocks hold its contents**, in a structure often called an **inode**. A directory maps names to inodes. Free blocks are tracked so they can be allocated.

### Surviving a crash
Creating a file changes several structures. If power fails between the writes, they disagree: a block marked used that belongs to no file, or a file pointing at a block that is free.

**Journaling** file systems first write a description of the change to a **journal**, then make the change, then mark it complete. After a crash, the journal is replayed or discarded, and the structures are consistent again. It is write-ahead logging, the same idea databases use. **Copy-on-write** file systems never overwrite live data: they write a new version and switch a pointer atomically.

### When is data really saved?
For speed, operating systems keep written data in memory and write it to the device later. A program that must be sure, such as a database committing a transaction, calls **fsync** to force it out. Skipping it is fast and loses data in a power failure.

### Redundancy
Devices fail. **RAID** combines several:

- **Mirroring** keeps identical copies on two devices.
- **Parity** schemes store data across several devices with extra parity, surviving one or two failures with less overhead than mirroring.

RAID protects against device failure. It is **not a backup**: a deleted or corrupted file is deleted or corrupted on every copy at once.

### Choosing
Use solid-state storage for anything with random access. Keep rarely used bulk data on cheaper media. Whatever you choose, keep tested backups elsewhere.

### Worked example
How a file system finds the bytes of a file on disk.

```text
Path:  /photos/cat.jpg
1. Read the root directory → entry "photos" → inode 12
2. Read inode 12 (a directory) → entry "cat.jpg" → inode 57
3. Inode 57: size 2,500,000 bytes; blocks 9100–9710 (4 KB each)
4. Read those blocks → file contents

Deleting cat.jpg removes the directory entry and frees the blocks;
the data stays on disk until overwritten.
```

Directories map names to inodes, and inodes map files to blocks; that indirection is why renames are instant and deleted data can sometimes be recovered.

> Key idea: Disks are slow to seek; flash must erase before writing and wears out. File systems use journaling or copy-on-write so that a crash cannot leave them inconsistent.

! Mechanical movement takes milliseconds.

- Compresses the disk

#LESSON Buses, drivers and the hardware interface | 13
A processor is useless alone. It reaches memory and devices over **buses**, and software reaches devices through **drivers**.

### Buses
A bus is a shared set of wires with a protocol. Conceptually there are three groups:

- the **address bus** says which location;
- the **data bus** carries the value;
- the **control bus** says whether this is a read or a write, and when.

The number of address lines sets how much can be addressed; the number of data lines how much moves at once. Modern machines use fast serial links instead of wide parallel ones: **PCI Express** for cards and fast storage, **USB** for external devices, **SATA** and **NVMe** for drives.

### Address decoding
When the processor puts an address on the bus, exactly one device must respond. **Address decoding** logic examines the high bits of the address and enables the right chip. Each device occupies a **range** of addresses, and the collection of ranges is the system's **memory map**.

```text
0x0000_0000 – 0x0FFF_FFFF    flash (program)
0x2000_0000 – 0x2001_FFFF    RAM
0x4000_0000 – 0x4000_0FFF    timer registers
0x4001_0000 – 0x4001_0FFF    serial port registers
```

### Talking to a device
A device exposes **registers**: a status register (is data ready? was there an error?), a control register (start, stop, configure) and data registers. Three ways for software to work with them:

- **Polling:** check the status register repeatedly. Simple, wastes processor time.
- **Interrupts:** the device signals when it needs attention. Efficient for events that are occasional.
- **Direct memory access (DMA):** the device transfers a whole block to or from memory by itself and interrupts once at the end. Essential for fast devices such as disks and network cards, where an interrupt per byte would swamp the processor.

### Device drivers
A **driver** is the software that knows one device's registers and protocol and presents a standard interface to the rest of the operating system: open, read, write, close. Applications use the same calls whatever the hardware. This is abstraction doing real work: a new printer needs a new driver, not new applications.

Drivers run with full privileges inside the **kernel**. A bug in one can crash the whole machine, and they are a common source of both crashes and security holes.

### User mode and kernel mode
Processors have at least two **privilege levels**. Application code runs in **user mode** and cannot touch hardware or other programs' memory. To do I/O, it makes a **system call**, which switches the processor to **kernel mode**, runs trusted operating-system code, and returns. The hardware enforces the boundary; it is the foundation of system security and stability.

### Starting up
When power is applied the processor begins executing at a fixed address in **firmware** (BIOS or UEFI on a PC). The firmware tests and initialises hardware, then loads a **bootloader**, which loads the operating-system kernel, which starts drivers and then the first programs. **Secure boot** checks a cryptographic signature at each step, so that tampered code is refused.

### Concurrency with hardware
A driver's interrupt handler can run at any moment, in the middle of other driver code. Shared data must be protected by disabling interrupts briefly or with locks designed for interrupt context. This is concurrency at its least forgiving.

> Key idea: Devices appear as registers at addresses in the memory map. Drivers wrap them behind a standard interface, and the processor's privilege levels keep applications away from the hardware.

- To encrypt addresses
* To make sure exactly one device responds to each address
- To speed up the clock
! It enables the chip whose address range contains the address.
#Q Why is DMA used for disks and network cards?
- It is more secure
* The device moves whole blocks to memory itself, avoiding an interrupt for every byte
- It needs no memory
! High data rates would otherwise overwhelm the processor.

#LESSON Designing a small computer system | 12
Computer engineering is the practice of choosing and combining hardware and software to meet a requirement within limits of cost, power, size and time.

### Start from requirements
- What must it do, and how fast?
- What does it connect to?
- What power is available: mains, a battery, energy harvested from light?
- What environment: temperature, vibration, moisture?
- How many will be made, and at what cost each?
- How long must it last, and how will it be updated?
- What happens if it fails?

A device made in millions is optimised to the cent. One made in tens uses a ready-made board.

### Choosing the processor
- A small **microcontroller** for simple control at microwatts.
- An **application processor** running Linux for cameras, displays and networking, at watts.
- An **FPGA**, whose logic is configured and not programmed, for very fast or highly parallel signal processing.

Choose the smallest that meets the need with margin. Development boards and reference designs reduce risk.

### Partitioning hardware and software
A function can be done in software (flexible, cheap to change, slower) or in dedicated hardware (fast, low power, costly to change). Filtering a signal might be an analogue circuit, a hardware block or a few lines of code. The split is a central design decision.

### The power budget
List every component with its current in each mode and the fraction of time in that mode:

```text
average current = Σ (current in mode × fraction of time in mode)
battery life (hours) = capacity (mAh) / average current (mA)
```

A sensor node drawing 20 mA for 100 ms each minute and 5 µA asleep averages about 38 µA, and a 220 mAh coin cell lasts roughly eight months. Shortening the awake time does far more than choosing a slightly more efficient processor.

### Timing budgets
For real-time behaviour, add up the worst case of every step from event to response: sensor delay, interrupt latency, computation, communication, actuator delay. The total must be inside the deadline with margin.

### Reliability
- **Watchdog timers** recover from hung software.
- **Brown-out detection** holds the processor in reset when the supply is too low to run correctly.
- **Checksums** on stored data and firmware.
- **Redundancy** for critical functions.
- Safe **default states**: if the controller fails, the heater turns off.
- For safety-critical products, development follows formal standards and is independently assessed.

### Testing hardware and software together
- Unit-test logic on a computer through a hardware abstraction layer.
- **Hardware-in-the-loop** testing connects the real controller to a simulated environment.
- Test at the extremes: low battery, temperature limits, noisy signals, power removed during a write.
- Build in **diagnostics**: a serial log, status lights, test points.

### Design for the whole life
Plan how the device will be manufactured and tested on the production line, updated securely in the field, repaired, and eventually recycled. A device that cannot be updated cannot be fixed.

### The engineer's judgement
Every choice trades performance, power, cost, size and development effort. There is rarely one right answer. Write down the alternatives you rejected and why.

> Key idea: Design from requirements and budgets. Sum the power and the worst-case timing before building, and plan for failure and for updates.

#LESSON Flash memory and data integrity | 12
### How flash differs from RAM
Flash memory keeps its contents without power, which is why it holds firmware, phone storage and SSDs. It has three rules that shape all software built on it:

- You can **read** any byte.
- You can **program** (write) a page, typically a few hundred bytes to a few kilobytes, but only change bits from 1 to 0.
- To set bits back to 1 you must **erase** a whole block, often tens or hundreds of kilobytes, and erasing is slow.

So "overwriting one byte" really means: copy the block's live data elsewhere, erase, and write it back.

### Wear
Each block survives only a limited number of erase cycles: roughly 100,000 for some microcontroller flash, and as few as a few thousand for dense consumer flash. A program that writes a counter to the same place every second would wear that block out in days.

**Wear levelling** spreads writes across all blocks by writing new data to fresh locations and keeping a map from logical to physical addresses. SSDs and memory cards do this in a controller; small devices use a flash file system or a log-structured store designed for it.

The extra internal copying means the device writes more than the program asked for, called **write amplification**. Keeping free space and writing in large sequential chunks reduces it.

### Errors and checksums
Bits can flip: from wear, radiation, or charge leaking over years. Defences come in layers:

- **ECC** (error-correcting codes) stored alongside data can fix small errors automatically; flash controllers rely on it.
- A **checksum** or **CRC** stored with each record detects corruption, so software can reject bad data rather than act on it.
- Critical settings can be stored twice and compared.

### Surviving power loss
Power can fail in the middle of a write, leaving half-written data. Safe designs never update in place. Instead:

1. Write the new version to a fresh location, with a sequence number and a CRC.
2. Only when it is complete, mark it as current (or let the higher sequence number win).
3. On start-up, pick the newest record with a valid CRC.

If power fails during step 1, the old version is still intact. This is the same idea as a database journal.

### Worked example
Saving a settings record safely on flash with two slots and a CRC.

```text
Slot A: seq 41, data {...}, CRC ok      ← current
Slot B: seq 40, data {...}, CRC ok

Write new settings:
  1. Erase slot B; write seq 42, data, then the CRC last.
  2. Power fails during step 1 → slot B has a bad CRC; boot picks slot A (seq 41).
  3. Write completes        → boot picks slot B (seq 42, highest valid).
```

Alternating slots with sequence numbers and a CRC written last means there is always one complete, valid copy, whatever moment power fails.

> Key idea: Flash is written in pages and erased in blocks, and wears out; spread writes with wear levelling, detect corruption with CRCs and ECC, and never overwrite in place when power can fail.

- Flash is read-only

- Each byte has its own password
! Erase works on blocks, so updates mean copy, erase and rewrite.
#Q What does wear levelling do?
- Encrypts the flash
* Spreads writes across all blocks so no block wears out early
- Makes reads faster
! Every block gets a share of the erase cycles.
#Q How do safe designs survive power loss during a settings update?

* By writing the new version to a fresh location with a CRC and only then treating it as current
- By disabling interrupts
! The old version stays valid until the new one is complete.

#LESSON Booting and updating devices | 12
### From power-on to your code
When a processor starts, it fetches its first instruction from a fixed place: the **reset vector**. What happens next is a chain of small programs, each preparing the ground for the next.

On a microcontroller the chain is short: built-in **boot ROM** code, then usually a **bootloader**, then the application. On a PC, firmware (**UEFI**, formerly BIOS) tests and initialises the hardware, finds a boot loader on a disk, which loads the operating system kernel, which starts everything else.

### What a bootloader does
- Sets up clocks and memory.
- Checks that the application image is present and valid (a CRC or signature).
- Offers a way to install new firmware, over USB, serial or a network.
- Jumps to the application.

Keep the bootloader small, well tested and rarely changed: if it breaks, the device may be unrecoverable ("bricked").

### Secure boot
Anyone who can change the firmware controls the device. **Secure boot** builds a **chain of trust**: the boot ROM contains a public key (or its hash) that cannot be changed; it verifies the bootloader's digital signature; the bootloader verifies the application's signature, and so on. Unsigned or altered code is refused. The private signing key must stay off the device and well protected.

### Updating safely in the field
Over-the-air (**OTA**) updates fix bugs and security holes on devices already sold, but a failed update must never leave a dead device.

- **A/B partitions:** keep two copies of the firmware. Download the update into the inactive slot while the device keeps working, verify it, then switch slots on the next boot.
- **Rollback:** if the new firmware fails to start or does not confirm it is healthy within a time limit, the bootloader switches back to the previous slot.
- **Anti-rollback counters** stop an attacker from reinstalling an old, vulnerable but validly signed version.
- **Delta updates** send only the changed bytes to save bandwidth and battery.

### Where this meets the rest of the course
Phones, routers, cars and smart speakers all follow this pattern, and so do app stores and the update systems of desktop applications: verify before installing, keep a known-good version, and switch over atomically.

### Worked example
An over-the-air update with A/B slots and rollback.

```text
Running slot A (v1.4). Update v1.5 arrives.
1. Download into slot B while v1.4 keeps working.
2. Verify signature and hash of slot B.
3. Set "try B once" and reboot.
4. v1.5 starts, runs self-tests, then marks itself "good".
   If it crashes or does not confirm within 60 s, the bootloader returns to A.
5. Anti-rollback counter raised only after "good", so v1.3 can never be reinstalled.
```

The device always keeps a known-good version, so a bad update costs a reboot rather than a dead product.

> Key idea: Booting is a chain from the reset vector through boot ROM and bootloader to the application. Secure boot verifies each link's signature, and A/B partitions with rollback make field updates safe.

- That it is smaller than the last one

! Each stage verifies the next, forming a chain of trust.

* So an update can be installed into the inactive slot and rolled back if it fails
- To double the storage
! The known-good version stays available.
#Q What is an anti-rollback counter for?
- Counting reboots
* Preventing the installation of an older, vulnerable firmware version
- Measuring battery life
! A signed old version may still have known holes.

function fromBytes(bytes, endian) {

  return ((b[0] << 24) | (b[1] << 16) | (b[2] << 8) | b[3]) >>> 0;
}

function swap16(value) {
  return ((value & 255) << 8) | ((value >> 8) & 255);
}

function splitAddress(address, pageSize) {
  return { page: Math.floor(address / pageSize), offset: address % pageSize };
}

function decode(address, map) {
  for (const d of map) {
    if (address >= d.start && address <= d.end) return d.name;
  }
  return null;
}

function checksum(bytes) {
  let sum = 0;
  for (const b of bytes) { sum = (sum + b) % 256; }
  return sum;
}

function parity(byte) {
  let ones = 0;
  for (let i = 0; i < 8; i++) { ones += (byte >> i) & 1; }
  return ones % 2;
}

function alignUp(address, alignment) {
  return Math.ceil(address / alignment) * alignment;
}

class RingBuffer {
  constructor(capacity) {
    this.capacity = capacity;
    this.data = new Array(capacity);
    this.head = 0;
    this.count = 0;
  }
  push(value) {
    if (this.count === this.capacity) return false;
    this.data[(this.head + this.count) % this.capacity] = value;
    this.count++;
    return true;
  }
  pop() {
    if (this.count === 0) return null;
    const value = this.data[this.head];
    this.head = (this.head + 1) % this.capacity;
    this.count--;
    return value;
  }
  size() {
    return this.count;
  }
}

function batteryLifeHours(capacityMah, modes) {
  let average = 0;
  for (const m of modes) { average += m.ma * m.fraction; }
  return Math.round(capacityMah / average * 10) / 10;
}

@hints
Extract bytes with shifts and a mask: `(value >>> 24) & 255` is the most significant byte. Little-endian is the same list reversed.
When rebuilding a number, finish with `>>> 0` so that values above 2 billion are not shown as negative.
The page number is the address divided by the page size, rounded down; the offset is the remainder.
A ring buffer needs an array, the index of the oldest item and a count. The next free slot is `(head + count) % capacity`.
Battery life is the capacity divided by the sum of current × fraction over the modes.
